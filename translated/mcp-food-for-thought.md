# API 做不成好的 MCP 工具

模型上下文协议（MCP）如今是件相当重要的大事。它已经成为让大语言模型（LLM）访问他人所写工具的事实标准，而这自然也就把它们变成了智能体。但为一个新的 MCP 服务器编写工具并非易事，因此人们常常提议把现有 API 自动转换成 MCP 工具；通常的做法是利用 OpenAPI 元数据（1、2）。

以我的经验来看，这条路行得通，但效果并不好。原因如下：

## 工具数量一多，智能体就应付不来

众所周知，VS Code 对工具数量有 128 个的硬性上限——但许多模型在远未达到这个数字之前，工具调用的准确性就已经力不从心了。此外，每个工具及其描述都会占用宝贵的上下文窗口空间。

大多数 Web API 在设计时根本没有考虑这些约束！如果是从代码中调用，一个产品领域拥有数不清的 API 也无可厚非；但如果把每个 API 都映射成一个 MCP 工具，结果可能就不怎么样了。

从头开始设计的 MCP 工具通常比单个 Web API 灵活得多，一个工具就能完成好几个独立 API 的工作。

## API 会迅速耗尽上下文窗口

想象一个 API 每次返回 100 条记录，而每条记录都非常宽（比如有 50 个字段）。把这些结果原样发给智能体会消耗大量 Token；即使查询只需几个字段就能满足，所有字段最终都会进入上下文窗口。

API 通常按记录数分页，但记录的大小可能相差悬殊。一条记录可能包含一个要占 100,000 个 Token 的大文本字段，而另一条可能只有 10 个。把这些 API 结果直接塞进智能体的上下文窗口是一场赌博；有时行得通，有时会撑爆。

数据格式也可能是个问题。如今大多数 Web API 返回 JSON，但 JSON 是一种 Token 效率非常低的格式。看这个例子：

```
[
 {
 "firstName": "Alice",
 "lastName": "Johnson",
 "age": 28
 },
 {
 "firstName": "Bob",
 "lastName": "Smith",
 "age": 35
 }
]

```

再对比一下同样的数据用 CSV 格式表示：

```
firstName,lastName,age
Alice,Johnson,28
Bob,Smith,35

```

CSV 数据要简洁得多——每条记录消耗的 Token 只有一半。通常情况下，CSV、TSV 或 YAML（用于嵌套数据）是比 JSON 更好的选择。

这些问题没有一个是无法解决的。你可以设想：自动添加工具参数让智能体投影字段，自动截断或总结过大的结果，自动把 JSON 结果转换成 CSV（嵌套数据则转成 YAML）。但我见过的大多数服务器，这些事一样都没做。

## API 无法充分发挥智能体的独特能力

API 返回结构化数据供程序使用。这往往是智能体希望从工具调用中获得的东西……但智能体也能处理其他更自由形式的指令。

例如，一个 ask_question 工具可以对某些文档执行检索增强生成（RAG）查询，然后以纯文本形式返回信息，用来指导下一次工具调用——完全跳过结构化数据。

或者，调用 search_cities 工具可以返回一个结构化的城市列表，外加一条关于接下来该调用什么的建议：

```
city_name,population,country,region
Tokyo,37194000,Japan,Asia
Delhi,32941000,India,Asia
Shanghai,28517000,China,Asia

Suggestion: To get more specific information (weather, attractions, demographics), try calling get_city_details with the city_name parameter.

```

在 MCP 服务器中，这种分层和工具链式调用可以非常有效；而如果把 API 自动转换成工具，你就会完全错过这一点。

## 如果智能体需要调用 API，直接调用就是了

如今像 Claude Code 这样的智能体非常擅长编写并执行代码，包括调用 Web API 的脚本。有些人甚至据此认为 MCP 根本没有必要存在！

我不同意这个结论，但我确实认为我们应该滑向冰球即将到达的地方。智能体的沙箱化正在迅速改进，如果智能体直接调用 API 既简单又安全，那我们不妨就这么做，省去中间环节。

## 结论

智能体与 API 的典型使用者有着根本性的不同。从现有 API 自动创建 MCP 工具是可行的，但这样做很可能效果不佳。只有为智能体独特的能力与局限而设计的工具，才能让它们发挥出最佳水平。
