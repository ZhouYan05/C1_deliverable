作为 GitHub 的资深工程师，代码审查是我日常工作中的主要关注领域之一。在过去八年里，我审查过 7,000 多个拉取请求。为什么这么多？因为代码审查对于构建优质软件至关重要，多一双眼睛往往能发现你原本会错过的问题。

我把代码审查视为我工作中最重要的方面之一。事实上，每当看到队友有拉取请求准备好接受代码审查时，我都会优先放下手头正在开发的分支，转而审查他们提出的改动。毕竟，他们的拉取请求已经通过了持续集成（CI）的重重考验，也达到了他们自己心中「完成」的标准，所以它很可能比我自己进行中的工作更接近可交付状态。我更愿意帮他们的代码冲过终点线，而不是再花不确定的时间打磨自己的代码。

我越早提供反馈——「这里可能为 nil 并导致错误」「这看起来像是一个 n+1 查询」「这里最好能有个方法签名」——这些反馈就能越早被处理，bug 就能越早被修复，功能就能越早上线。

我想分享一下我进行代码审查的方式，希望我们都能交付更好的代码。

## 什么是代码审查？

严格来说，代码审查——通过 GitHub 上的拉取请求审查进行——允许协作者对拉取请求中提出的改动发表评论、表示赞同，或在拉取请求合并前要求进一步修改。

我把拉取请求看作对话的开始。我读它时，理解为作者在说：「我认为这比我们现有的更好。」代码审查是塑造产品实现的好机会。作为代码审查者，我的职责是与作者反复讨论，通过提问、质疑假设、充当第二双眼睛来改进他们的代码。

## 优化你的代码审查流程

### 如何找到待审查的拉取请求

我生活在 GitHub 通知收件箱里。它是我浏览器固定标签页中仅有的几个之一，所以随时可用。每当我在等待 CI、处于任务间隙、开始一天的工作、或手头有空的时候，我都喜欢查看收件箱。我审查的大多数拉取请求都是在那里发现的。GitHub 的团队往往把某个 Slack 频道当作大本营，那是分享待审查拉取请求的好地方——这也是我发现拉取请求的另一条主要途径。

我还喜欢使用 GitHub 的 Slack 集成，让 Slack 频道订阅与团队相关的新拉取请求。为了筛选出现在 Slack 中的拉取请求，我会使用团队专属的标签，然后在 Slack 中使用「subscribe」命令，比如 /github subscribe your/repo pulls +label:"your-team-label"。

我喜欢用这样的查询来搜索可能待审查的拉取请求：is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team。通过这个查询，我能找到 GitHub 组织内处于开启状态、未归档、非草稿、且请求了相关代码所有者团队作为审查人的拉取请求。我通常会省略 review:required 搜索限定符，因为即使队友已经审查过某个拉取请求，我也有兴趣再审查一遍。毕竟，审查代码不仅帮助作者，也帮助我及时了解影响我所负责代码的改动。

### 使用审查人团队管理通知

你不希望代码改动通知到过于庞大的团队，以至于团队里每个人都认为审查该改动不是自己的责任。这可能导致拉取请求要么无人审查而被搁置，要么在时机未到时就提前合并，因为关键审查人淹没在通知洪流中错过了它们。这两种情况都会影响产品质量。

如果可以的话，我建议精简你所在的代码所有者团队数量，让通知保持在可控范围内。这样，落入你收件箱的拉取请求就不只是噪音，而是你真正觉得应该审查的东西。虽然大而全的代码所有者团队作为兜底方案可以接受，但它们并不适合作为自动审查请求的一线默认选项。让你仓库的 CODEOWNERS 文件保持井井有条，并配套清晰的代码边界，以限制通知量，帮助审查人避免通知疲劳。

另一种限制团队通知的方法是创建一个「第一响应人」团队，然后用自动化按排班添加和移除团队成员。这样你的团队可以专注于日常代码库，而轮值的第一响应人会收到团队服务领域内拉取请求的通知。例如，使用 PagerDuty API，你可以确定某天谁是第一响应人，然后用 Octokit 库来添加和移除团队成员。

### 用自动化在团队间统一代码审查标准

仓库级别的配置和自动化，例如使用 CODEOWNERS 文件和分支保护规则，有助于在团队间强制执行审查流程标准。其他标准，比如拉取请求中什么值得评论，必须由我们人来维护。记录团队内部代码审查的工作方式，确保任何提供代码审查或提交拉取请求的人都了解如何让自己的拉取请求被审查、预期的审查响应时间，以及使用了哪些自动化来辅助审查。

有些团队用项目看板来跟踪哪些拉取请求进入审查；我见过这对管理共享 API 的团队很有效，因为这类领域经常被团队外的人修改。其他团队只依赖 GitHub 通知，我见过这在代码所有权划分清晰、团队对及时审查拉取请求足够自律的情况下效果很好。

如果你的流程是团队独有的，自动化可以帮助与团队外的人沟通预期。例如，如果许多其他团队依赖你团队的审查，你可以用机器人自动在任何请求你团队审查的拉取请求下留言，告诉作者什么时候能收到你们的反馈。

## 什么样的代码审查是好的，什么样的是糟糕的？

好的代码审查能厘清问题，推动代码走向比起点更好的状态。

作为审查人，沟通清晰是关键。你要明确哪些评论是个人偏好，哪些是批准前的阻塞项。为你建议的方法提供示例，能提升代码审查的质量，让你的意思更清楚。如果你能从拉取请求所在的同一仓库中找到示例，那就更好了——这通过鼓励一致的实现，进一步支持你的建议。

相比之下，糟糕的代码审查缺乏清晰度。例如，没有任何评论的笼统批准或拒绝，会让拉取请求作者怀疑审查是否认真。哪怕只是在批准时复述你对拉取请求作者意图的理解，也能暴露你和作者的理解是否一致。

审查对建议何时实施含糊不清，对作者来说也是糟糕的体验。指出现有未改动的代码应该重构、或者某个额外情况应该处理，都没问题，但重要的是说明这些是否是批准的前置条件。如果拉取请求不采纳你的建议也可以合并，务必说明。让改动集（diff）保持小巧、把这些改动拆分到单独的拉取请求中交付，可能更稳妥。

下面这条代码审查评论展现了具体性，并清晰地传达了建议的实现方式：

> 「我看到你的新方法与这个文件中现有风格一致，接收 [X] 个参数。参数太多会损害可读性，也意味着这个函数做了太多事情。你觉得在之后的拉取请求里重构这个方法和现有的方法、减少参数数量怎么样？」

这条评论做得好的地方：

- 提供了具体细节。
- 引用了具体的代码或 issue。
- 为问题提出了解决方案。
- 引用了证据或给出了解释。

作为反面例子，下面是一些可以写得更好的审查评论：

> 「我不喜欢这个。」——审查人不喜欢什么？他们心里是否有替代方案可以明确说出来？

可以改进为：

- 「这一行做了太多事情，我们能简化它来提高可读性吗？」
- 「我认为这会有性能问题，因为存在 n+1 查询。」
- 「我们能用 [首选框架] 的解决方案，而不是自己写一套实现吗？」

> 「这样不行。」——为什么这些改动不行？

可以改进为：

- 「这样不行，因为 [X]，请参见这个相关的 issue：[issue 链接]。」
- 「之前在 [拉取请求链接] 里试过这个方案，但因为 [X] 没有成功。」
- 「如果你在 [X] 上遇到问题，可以试试 [替代方案]。」

> 「我觉得这修复了一个 bug。」——我很欣赏这样的提醒，但有没有额外的上下文（比如 issue 链接）能让它更清楚呢？

可以改进为：

- 「我觉得这修复了 [issue 链接]。」
- 「这是修复 [issue 链接] 里的那个 bug 吗？」
- 「这看起来像我们在 [失败的构建链接] 里遇到的那个 bug。感谢修复！」

## 如何给出好的代码审查

### 提问

我把拉取请求作者视为对其改动上下文最了解的人。我可以根据我的过往经历——比如在 Ruby on Rails 单体应用、TypeScript、以及高流量数据库方面的经验——指出我看到的问题，但我相信作者对我问题的回答。我认为他们对具体细节的理解比我更准确。

我也喜欢问涉及代码中假设的问题。他们处理的数据是什么形态？是否存在不符合这种形态的数据？代码对此处理得好吗？代码是否资源密集？性能会好吗？作为审查人，我最喜欢的回应是作者提供一个自动化测试来验证这些场景下的行为。第二喜欢的回应是经验数据，比如来自我们数据仓库的查询或 Datadog 图表，说明这些场景为什么不是问题。

作为拉取请求作者，我很感激收到提问。有人提问时，我就有机会解释为什么我对自己的改动有信心，必要时引用 issue、查询或图表。这也让我能与他人分享知识和经验。不仅作者能看到我的回复，其他审查人和未来追查过往决策背景的读者也能看到。

### 给予肯定

除了提问，评论拉取请求中你同意的部分也是好习惯。这些评论可以表明你阅读并理解了改动内容，或者你验证了代码中的某个假设。举几个例子：

- 「看起来这与本模块中其他类使用的模式一致。」
- 「感谢你为此添加了测试！」
- 「这比之前可读多了。」

以我的经验，收到这样的评论也确实让人很开心。接受代码审查有时会让人感到疲惫。当我疲于应对多方的提问和建议时，收到几条不要求我做什么、反而支持和认可我已付出努力的评论，会是很好的鼓励。

### 注意偏见和假设

很容易让你对审查人的偏见，或对他们正在修改的代码领域的偏见，影响你的审查。你习惯了某个人在某个领域工作、或具备一定资历，就会默认他们知道自己在做什么——但每个人都会犯错。你的目光落在他们的改动上，你的问题检验他们的假设、或验证你自己的假设，就能在问题部署之前发现它。

我非常推崇写测试，因为测试能消除一部分偏见。当你写测试来检查代码是否正常工作时，你不需要只凭作者的一面之词，只需要看测试是否通过——当然，前提是你的测试写对了。😅

我也非常推崇初级开发者在代码审查中向资深开发者提问，即使他们觉得自己的问题很蠢、或者答案显而易见。如果对你来说不显然，那这个问题就是合理的。对别人来说也不会显然！大胆提问，给作者留出写下答案的空间，把这份知识保留给后来的人。

### 批准还是不批准

我把自己的审查视为一道可能阻止他人改进我们产品的关卡，所以我在批准时会保持审慎。我经常会有个人偏好，建议一些我希望作者做出的可选改动，但我不会仅仅因为这些就拒绝批准。如果我对某人的拉取请求有建议，但按原样合并不会破坏生产环境、负面影响用户或造成其他问题，我会在附上这些评论的同时批准。作者可以选择在合并拉取请求前处理我的反馈，也可以在另一个分支里跟进。

在审查代码时，要掂量你的建议有多重要。它值得推迟发布来落实吗？值得作者经历看到反馈、做出建议改动、等待 CI、再次审查、部署、最终合并这一整个循环吗？如果某个建议缺席不会让任何人的日子变得更糟，那就让作者决定是否以及何时采纳。

「请求修改」选项会阻止拉取请求被合并，直到审查人回来批准为止。我很少使用它，因为它通常显得过于强硬。我相信我的团队知道何时该批准拉取请求，所以队友的批准足以代替我的。同样，我也相信拉取请求作者会尊重并考虑我的反馈，而不是因为别人批准了而我没批准就盲目合并。我几乎只在认为存在紧迫的安全问题、并且担心他们在合并前看不到我的顾虑时，才会选择「请求修改」。

## 如何从代码审查中获益最多

### 审查自己的代码

GitHub 资深软件工程师 Paul Smith 教会我在请别人审查之前先审查自己的拉取请求，我也建议你这么做。先从头过一遍，在那些不明显的改动上留下行内评论，或者留下那些你在别人的拉取请求里看到会提问的评论。自我审查还有助于判断拉取请求是否太大、是否值得拆分。

顺便推荐：如果你在意保持拉取请求小巧，可以使用 lerebear/sizeup-action 自动给拉取请求打上标签，标明其复杂度和规模。

### 欢迎合并后的审查

如果我碰巧在别人有机会审查之前就合并了拉取请求，我仍然欢迎他们的审查。如果我的拉取请求破坏了什么、或产生了意外后果，在拉取请求上评论说明，会留下线索，帮助未来的读者弄清发生了什么！

如果我收到对已合并拉取请求的审查，我会像拉取请求落地前一样处理反馈。可能是用评论解释我的观点，可能是用新的拉取请求迭代我最初交付的代码，也可能是新建 issue 来记录待完成的额外工作。

### 使用草稿拉取请求

当你创建新拉取请求时，可以选择将其设为草稿。我非常依赖草稿阶段来表明我是否想要审查。例如，如果必需的 CI 构建失败了、或我还没做完，我就会保持草稿状态。我也倾向于对别人的拉取请求抱有同样的预期：如果是草稿，我假定作者还没准备好接受审查。如果标记为就绪待审，我就假定他们离部署只差获得足够的批准。

草稿状态意味着拉取请求尚未完成，所以我在解决合并冲突或处理审查人反馈时，会把拉取请求移回草稿状态。如果我必须修改代码，我会先把拉取请求标记为草稿，以免打扰已经审查过的人。当我把它移回「就绪」状态时，GitHub 会向那些审查人发送通知，让他们可以再看一遍。

### 保持友善

我想起一句谚语：「蜂蜜比醋能抓到更多苍蝇。」我希望自己的拉取请求收到审查，所以我喜欢回复我拉取请求下的评论——尤其是当我不同意审查人的时候。即使我不写回复，我也经常会用 👍 表示同意，或用 ❤️ 表示感谢。

我希望审查人相信他们的建议不会被遗忘，所以我会通过评论让他们随时了解进展。如果我同意他们的建议——例如进一步重构现有代码——我会表示赞同，但同时也会提出这个改动不适合放在当前拉取请求里。当我在之后的拉取请求中处理他们的反馈时，我会回来附上链接，让审查人知道他们的反馈没有被忽视。

我还会在之后实现这些建议改动的拉取请求中 @ 他们，并附上说明，比如「这是对 @某某 在 <上一个拉取请求 URL> 中反馈的回应。」这既为其他读者提供了背景，也是对最初审查人的致谢，把功劳归于提出这个想法的人。

当你兑现承诺、在之后的分支中落实反馈时，就能与审查人建立信任，让他们更放心批准你未来的拉取请求，因为他们知道你不会把事情半途而废。

## 结语

代码审查对产品质量的重要性怎么强调都不为过，尤其是在 AI 代码生成的时代。在我的职业生涯中，许多次 bug 被捕获、事故被避免，仅仅是因为多了一双眼睛。代码审查完全值得投入时间，无论是花在日常审查上、打磨流程上，还是构建支持它的自动化上。对开发者来说，现在彻底审查拉取请求，远比之后处理一个已经上线到生产环境的问题更快、更省心。

感谢你如此重视代码质量，愿意读完我的代码审查理念。你最近查看过你的审查队列吗？也许现在是时候把这些想法付诸实践了。

如果你想进一步了解如何在 GitHub 上使用拉取请求审查，请查看 GitHub Community 上资深 DevOps 架构师 Mickey Gousset 和资深 DevOps 架构师 Joshua Johanning 讨论《审查拉取请求的 5 个技巧》的帖子。
