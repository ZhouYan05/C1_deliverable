# SAST vs. DAST vs. RASP：应用安全测试方法对比

学习
2024 年 12 月 18 日
Shanika Wickramasinghe

到 2025 年，全球信息安全支出预计将达到 2120 亿美元，比 2024 年增长 15%。据 Gartner 称，生成式 AI 的兴起和云计算的普及是这一快速增长的关键原因。该分析机构还预测，到 2027 年，GenAI 将在所有网络攻击中占 17% 的比例。

企业需要超越传统方法的高级安全策略，以应对这些日益增长的威胁。因此，企业主需要了解 SAST、DAST 和 RASP 等安全解决方案，因为它们能为应用提供多层防护。

（相关阅读：应用安全详解与常见软件测试方法。）

## 什么是 SAST？

静态应用安全测试（SAST）是一种白盒安全测试方法。SAST 利用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对其代码进行分析。

开发人员使用 SAST 检测各种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出以及代码中的其他 OWASP 漏洞。由于仅靠 SAST 无法识别运行时特有的漏洞，开发人员通常必须将 SAST 与其他测试方法结合使用，以实现全面的安全保障。

SAST 是软件开发生命周期（SDLC）的重要组成部分，因为它能够尽早发现漏洞。发现得越早，修复成本就越低。由于 SAST 工具可以在开发阶段执行，开发人员如今甚至可以在产品发布到市场之前，对代码进行上千次（!!）的编写和测试。

SAST 可以集成到 CI/CD 流水线中，集成之后即被称为"安全 DevOps"或"DevSecOps"。通过自动化，SAST 具有广泛的可扩展性。能够实施覆盖 SAST 技术的自动化测试，使其成为快速应对代码级风险的高效解决方案。

## 什么是 DAST？

动态应用安全测试（DAST）是一种黑盒测试方法。DAST 中的"动态"（Dynamic）一词表明，该方法在应用运行时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它会：

- 模拟外部攻击者的行为。
- 从外部对应用进行测试，以识别仅在运行时才会出现的漏洞。

DAST 能够识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用对这些模拟威胁的响应方式。借助这种方法，开发人员可以发现 SAST 等静态测试方法可能遗漏的弱点。

通常，开发人员在软件开发生命周期的后期阶段执行 DAST，往往就在部署之前。通过在真实运行环境中测试应用，DAST 清晰地呈现了运行时安全状况，并帮助应用以更佳性能抵御潜在攻击。

## SAST 如何工作？

开发人员使用 SAST 工具应用预定义规则和其他检测方法（如模式匹配和数据流分析）来识别编码错误及其他漏洞。他们将这些工具集成到 IDE 或 CI/CD 流水线中，以便在编码和测试阶段自动执行扫描。

### SAST 的常用方法

以下是 SAST 中使用的一些方法。

模式匹配：扫描代码库，查找已知的不安全编码实践模式。例如，使用弱加密算法或不安全的 API 调用。

数据流分析：跟踪数据在应用中的流动方式。通过追踪不受信任的输入到达敏感操作的路径，可以识别 SQL 注入或缓冲区溢出等漏洞。

控制流分析：分析应用的控制结构。例如，通过分析循环和条件语句来发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建：许多工具允许开发人员创建自定义规则，以践行编码最佳实践。以下是一些自定义规则示例：

- 标记在 SQL 查询中使用未经清理输入的任何情况。
- 识别将用户提供的数据输出到浏览器却未进行正确转义的代码。
- 高亮显示易受攻击或已弃用函数的使用，例如 JavaScript 中的 eval() 或 C 中的 strcpy()。
- 检测源代码中硬编码的 API 密钥和密码，并标记任何缺少对用户提供数据进行输入验证的位置。

依赖扫描：一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖项中的漏洞。

语义分析：通过解读代码的含义而不仅仅是其结构，SAST 工具可以检测不安全的配置或 API 的误用。

机器学习模型：先进的 SAST 工具结合机器学习算法，通过分析大型数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具通常需要大量的 CPU 和内存资源。在分析大型代码库时，这可能是一个重大问题。对一百万行代码进行全面扫描可能会消耗数 GB 的内存。

SAST 扫描所需的时间会因代码库规模的不同而有很大差异，从小型项目的几分钟到企业级应用的数小时不等。这可能影响：

- 构建流水线的时间进度
- 开发人员的工作效率

请考虑使用支持增量扫描的现代 SAST 工具，这样你只需分析发生变更的代码，而不必扫描整个代码库。

此外，通过规则选择和范围界定进行性能调优至关重要。配置不当的 SAST 工具可能会不必要地分析非关键代码路径，浪费时间和资源，却无法带来安全收益。

## DAST 如何工作？

DAST 工具模拟真实世界的攻击——例如，将各种形式的恶意数据发送到输入字段，观察应用如何处理这些数据——以识别应用行为和响应中的漏洞与弱点。

### DAST 的步骤

该过程通常包括以下步骤。

第 1 步：扫描。扫描 Web 应用以发现入口点（如 URL、表单和 API）。此步骤描绘出应用的结构并识别潜在的攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求试图利用入口点，以测试跨站脚本和跨站请求伪造等漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它评估应用在受到攻击时是否表现出预期行为。例如，可以注入恶意数据以检测 SQL 注入漏洞。

第 4 步：报告。生成包含已检测漏洞和修复建议的报告。开发人员可以利用报告中的结果修复已发现的问题。

现代 DAST 解决方案可以融入 AI 驱动分析和实时数据集成等高级功能。它们会自动创建测试集，动态适应应用的结构，并利用机器学习算法最大限度地减少误报。

### 使用 DAST 工具时的性能考量

以下是使用 DAST 工具时需要注意的一些性能瓶颈。

- DAST 工具与运行中的应用积极交互，会暂时增加应用服务器和 Web 服务器的 CPU 与内存使用量。
- DAST 扫描期间产生的大量并发请求可能消耗大量网络带宽。
- DAST 扫描器通过生成唯一请求，常常绕过应用缓存或使其失效，从而降低缓存机制的有效性。
- DAST 工具创建和管理多个测试会话会增加应用服务器的内存使用量。

为避免此类问题或尽可能降低其影响，请遵循以下实践。

- 将 DAST 扫描安排在应用使用量最小的非高峰时段。
- 在与生产环境配置一致的预发布（staging）或预生产环境中执行扫描。
- 使用 DAST 工具的限流功能控制并发请求的数量。
- 在扫描期间增大应用服务器线程池。
- 为 DAST 扫描器的 IP 配置单独的缓存策略。
- 如果超出性能阈值，则自动暂停扫描。

## SAST 与 DAST：主要区别

下表总结了 SAST 与 DAST 之间的区别。

| 标准 | SAST | DAST |
| --- | --- | --- |
| 测试类型 | 白盒测试。在可访问源代码的情况下，从内到外测试应用。 | 黑盒测试。在不访问源代码的情况下，从外部测试应用。 |
| 支持的软件类型 | 支持各种类型的软件，包括 Web 应用、Web 服务和胖客户端。 | 支持 Web 应用和 Web 服务，但通常不支持其他类型的软件。 |
| SDLC 中的阶段 | 在软件开发生命周期的早期执行。 | 在 SDLC 后期执行，通常在部署期间或部署之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞和应用级缺陷。 |
| 修复漏洞的成本 | 成本较低，因为问题在 SDLC 早期即被发现。 | 成本较高，因为漏洞发现较晚，往往需要紧急修复才能按时部署。 |
| 运行时和环境问题 | 无法检测运行时特有或与环境相关的漏洞。 | 可以识别仅在运行时或因环境因素才出现的漏洞。 |
| 深度与广度 | 提供对代码级漏洞的深入洞察。 | 提供应用外部安全风险的广泛视图。 |
| 工具集成 | 与 IDE 和 CI/CD 流水线集成，实现自动化静态分析。 | 与 CI/CD 流水线集成，实现持续的运行时测试。 |
| 误报与漏报 | 由于深入的代码分析，误报几率较高。 | 误报较少，但由于内部可见性有限，漏报风险较高。 |
| 技术依赖性 | 依赖于编程语言和框架；要求与工具兼容。 | 与应用框架无关，因为它们从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点

- 在软件开发生命周期早期识别安全漏洞。
- 分析代码库，包括基本函数和复杂分支。
- 直接对源代码进行操作，无需运行应用。
- 提供实时反馈和全面的洞察，例如漏洞的确切位置。
- 生成可导出的报告，可通过仪表盘进行跟踪。
- 支持自动化，比人工代码审查更快、更高效。

### SAST 的缺点

- 经常产生大量误报，因此可能需要人工审查。
- 无法识别运行时或环境特有的漏洞，例如配置错误。
- 需要针对每种编程语言使用特定工具，因此维护复杂。
- 难以理解外部库、API 和 REST 端点。

### DAST 的优点

- 识别仅在应用执行期间才会出现的漏洞。
- 从外部运行，无需访问源代码，这对测试第三方应用或已编译的代码十分有效。
- 模拟真实的攻击场景，识别 SAST 遗漏的风险。
- 独立于应用的编程语言工作。
- 评估整个应用和系统，包括内存消耗、资源使用和第三方接口。

### DAST 的缺点

- 只关注应用的外层，可能遗漏更深层的漏洞。
- 在 SDLC 后期才应用，因此修复成本更高、耗时更长。
- 会漏掉 SAST 工具通过源代码分析能够识别的某些漏洞。例如，假设一个 Web 应用使用不安全的随机数生成器（如 JavaScript 中的 Math.random()）来生成会话令牌。DAST 可能会漏掉这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到它。）
- 大型项目需要定制的基础设施，并需要多个应用实例并行运行，因此资源密集。

## 何时应使用 SAST，何时应使用 DAST？

SAST 和 DAST 在保障 SDLC 安全方面发挥着互补作用。了解每种工具的使用时机有助于实现全面的安全覆盖。

### 何时使用 SAST

在开发早期阶段。开发人员使用 SAST 在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署前发现这些问题，可以降低修复的成本和复杂度。

例如：SAST 工具扫描 Python 代码，标记出源代码中嵌入了硬编码 API 密钥的漏洞。开发人员重构代码，改用环境变量来安全地存储和获取密钥。

用于代码审查。SAST 可集成到版本控制系统中，使开发人员能够在提交代码之前进行扫描。这能确保只有安全的代码才会进入代码仓库。

示例：SAST 工具可以检测到这样的漏洞：文件路径直接由用户输入构造而成，未经任何验证，使应用面临路径遍历攻击的风险。开发人员通过清理输入并使用安全的库函数处理文件路径来修复该问题。

在持续集成/持续部署（CI/CD）流水线中。SAST 在 CI/CD 过程中运行自动化扫描，为开发人员提供实时反馈。

### 何时使用 DAST

预生产测试。开发人员使用 DAST 在预发布或 QA 环境中识别运行时漏洞（例如：不安全的配置、认证缺陷、访问控制不足）。

示例：DAST 工具可以检测到导致敏感数据暴露的数据库错误配置。随后开发人员可以在部署前修复该配置。

用于部署后监控。DAST 工具持续扫描已部署的应用，查找由环境变化或新出现的威胁引起的漏洞。这能保证应用长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，识别第三方 API 或互联系统中的漏洞。

例如：DAST 工具测试一个 Web 应用，发现第三方支付 API 存在漏洞：信用卡信息通过未加密的 HTTP 连接传输。开发人员通过强制所有 API 通信使用 HTTPS 解决了该问题。

## SAST 和 DAST 哪个更有效？

SAST 或 DAST 的有效性取决于：

- SDLC 阶段
- 需要应对的漏洞类型

SAST 在早期开发阶段效果最佳，主要用于识别源代码中的漏洞、降低成本并推广安全编码实践。相比之下，DAST 专注于预生产环境或已部署应用中的运行时漏洞，提供对错误配置和不安全集成等问题的洞察。

### 采用混合方法

与其二选一，不如将 SAST 和 DAST 结合使用，形成一种多层安全策略，同时应对静态代码和运行时环境中的漏洞。SAST 可以集成到早期开发阶段，在应用编译之前检测并修复代码级问题。当应用在测试环境中运行后，DAST 可以识别运行时漏洞，并评估应用在攻击条件下的行为。

在 CI/CD 流水线中自动执行 SAST 和 DAST 扫描，可以提供持续反馈，在不牺牲安全性的前提下加快开发进程。

对于敏捷或 DevOps 环境，添加 IAST 或 RASP 等工具可以进一步增强安全性。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

### 使用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（RASP）是一种高级安全解决方案，直接安装在应用运行的服务器上。

RASP 将自身嵌入应用的运行时环境。这种集成使 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

- 在异常行为发生时实时检测。
- 立即阻止恶意活动。

一个关键区别在于，RASP 不仅会对潜在问题发出警报，还会主动阻止攻击，无需依赖外部工具即可隔离并化解威胁。

RASP 为 SAST 和 DAST 提供了一种动态替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 实时运行。它在执行期间监控应用的行为，并通过终止会话或向防御人员发出警报来应对实时威胁。

RASP 在保护应用免受绕过网络防御或在开发阶段被遗漏的漏洞侵害方面尤为有效。

然而，对 RASP 的过度自信可能导致组织忽视安全编码实践。此外，由于 RASP 直接在应用的运行时环境中运行，可能会影响应用性能。RASP 无法取代修复底层缺陷的必要性，但它可以在修复工作进行期间提供持续保护。

正如一位 RASP 用户所说：

"是否使用 RASP 工具，应基于对应用具体需求和风险状况的全面评估。"

## 未来：SAST、DAST 与 RASP 相结合的应用安全测试

应用测试的未来在于将 SAST、DAST 和 RASP 结合起来，形成全面的安全策略。随着安全挑战日益增多，将这些工具集成到 CI/CD 流水线中并实现流程自动化将变得至关重要。

AI 和机器学习的进步将使测试更加高效，因为它们有助于减少误报并改进威胁检测。

### 金融与金融服务行业

在金融领域，AI 驱动的工具将改变漏洞的检测与缓解方式。SAST 和 DAST 将继续在开发和预生产阶段识别编码缺陷和运行时问题。

但这还不够：RASP 将更进一步，利用 AI 监控实时交易。例如，RASP 可以检测异常模式（例如：攻击者试图实时利用某个漏洞），在阻止这些活动的同时通知安全团队。

### 物联网、边缘计算与互联设备

在物联网（IoT）领域，这些工具的组合将在保护互联设备方面发挥重要作用。具体方式如下：

- SAST 可以确认固件在开发阶段不存在漏洞。
- DAST 可以测试设备之间通信协议的安全性。
- 与此同时，RASP 监控已部署的设备，检测并阻止由新出现的威胁引起的未授权访问尝试或数据泄露。

同样，使用多种方法将有助于物联网生态系统保持韧性。正如我们在众多示例中所说明的，SAST、DAST 和 RASP 三者结合，有望带来一个以更强大、更主动的安全措施构建和部署应用的未来。

## 强韧的安全始于主动测试

将 SAST、DAST 和 RASP 结合使用，可以提供覆盖整个软件开发生命周期的强大安全保障。

通过将这些方法集成到 CI/CD 流水线中并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一种整体性方案，保护现代应用免受安全漏洞的侵害。
