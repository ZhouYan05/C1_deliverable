## 概述

当前最新发布版本为 **OWASP Top Ten 2025**。
历史版本见 OWASP Top Ten 2021 与 OWASP Top 10 2017（PDF），更早版本可在 GitHub 仓库中找到。

OWASP Top 10 是面向开发者与 Web 应用安全领域的**标准意识文档**，它代表了业界对
Web 应用最关键安全风险的广泛共识，是全球开发者公认的「迈向更安全编码的第一步」。

企业应当采纳本文件，并启动确保自身 Web 应用尽量降低这些风险的过程。采用 OWASP
Top 10，或许是把组织内部的软件开发文化转变为「产出更安全代码」的**最有效第一步**。

## OWASP Top 10 2025 数据分析计划

### 目标

收集迄今与已识别应用漏洞相关的**最全面数据集**，以支撑 Top 10 的排序分析及未来研究。
数据应来自多种来源：安全厂商与咨询机构、漏洞悬赏计划（bug bounty），以及企业/组织的
贡献。数据将做归一化处理，以便在「人辅助工具（HaT）」与「工具辅助人（TaH）」之间做
层级对比。

### 分析基础设施

计划依托 OWASP 的 Azure 云基础设施来收集、分析和存储所贡献的数据。

### 贡献方式

计划同时支持实名与匿名贡献，并**优先鼓励实名贡献**——这对所提交数据的验证、质量与
可信度有极大帮助。若提交者希望数据匿名存储，甚至以匿名方式提交，则该数据将被标记为
「未经验证（unverified）」而非「已验证（verified）」。

| 场景 | 描述 |
|---|---|
| 场景 1 | 提交者实名，且同意被标识为贡献方 |
| 场景 2 | 提交者实名，但不希望被公开标识 |
| 场景 3 | 提交者实名，但不希望记录进数据集 |
| 场景 4 | 提交者完全匿名（待定是否支持） |

当未经验证的数据参与分析时，分析报告中会**明确区分标注**。

贡献渠道：将 CSV/Excel 文件邮件发送至项目邮箱，或上传至项目指定的短链接地址。
模板示例见 GitHub 仓库的 `2025/Data` 目录。

**贡献期**：计划接受截至 2025 年 7 月 31 日的贡献，数据时间范围为 2021–2024 年。

### 数据结构

最低限度需要：**时间段**、**数据集中受测应用总数**、**CWE 列表及各自命中的应用数量**。
信息越完整，分析越准确。此外强烈建议提供以下元数据：

- 贡献者名称（机构或匿名）
- 贡献者联系邮箱
- 时间段（2024 / 2023 / 2022 / 2021）
- 受测应用数量
- 测试类型（TaH 工具辅助人 / HaT 人辅助工具 / Tools 纯工具）
- 主要语言（代码语言）
- 地理区域（全球 / 北美 / 欧盟 / 亚洲 / 其他）
- 主要行业（多选 / 金融 / 工业 / 软件 / 其他）
- 数据是否包含复测或同一应用多次出现（是/否）

**CWE 数据**：CWE 列表 + 命中该 CWE 的应用数量。请尽量提供**具体的 CWE 而非 CWE
类别**，以便于分析与归一化。

> **注**：若贡献者同时拥有 HaT 与 TaH 两类数据，建议拆分为两个独立数据集提交。
> HaT = 人辅助工具（量大/频次高，主要来自工具扫描）；TaH = 工具辅助人（量小/频次低，
> 主要来自人工测试）。

### 调查问卷

与 Top Ten 2021 类似，计划通过问卷识别最多两个「社区认为重要、但数据尚未反映」的
风险类别。问卷中的 CWE 将来自当前趋势性发现、数据中落在 Top Ten 之外的 CWE，以及
其他潜在来源。

### 方法论

- 计划对数据做一定程度的**归一化**，同时保留原始数据版本以供未来分析。
- 分析数据集中 CWE 的分布，必要时对部分 CWE 重新归类、合并到更大的桶中；所有归一化
  操作都会被详细记录。
- 沿用 2021 年的模型，以**发生率（incidence rate）**而非频次（frequency）来衡量
  「某个应用至少含一个该 CWE 实例的可能性」——即统计**含该 CWE 的应用数**占受测
  应用总数的比例，而非报告数量。
- 此外将为前 20–30 个 CWE 计算基础 CWSS 分数，并将潜在影响纳入 Top 10 的权重计算。

## 十大风险速查表（补充参考）

> 下表为 **OWASP Top 10:2021** 的风险条目名称清单，用于对照学习。**并非本页抓取内容**，
> 来自该版本的公开标准条目（CC BY-SA 4.0）。完整描述请查阅官方文档或 2021 简体中文版。

| 编号 | 英文 | 中文 |
|---|---|---|
| A01 | Broken Access Control | 访问控制失效 |
| A02 | Cryptographic Failures | 加密机制失效 |
| A03 | Injection | 注入 |
| A04 | Insecure Design | 不安全设计 |
| A05 | Misconfiguration | 安全配置错误 |
| A06 | Vulnerable and Outdated Components | 易受攻击和过时的组件 |
| A07 | Identification and Authentication Failures | 身份识别和身份验证失效 |
| A08 | Software and Data Integrity Failures | 软件和数据完整性失效 |
| A09 | Security Logging and Monitoring Failures | 安全日志与监控失效 |
| A10 | Server-Side Request Forgery (SSRF) | 服务端请求伪造 |

**与本课程 Week 6 的关联**：A03（注入）与 A01（访问控制）在 AI 辅助编码场景下被显著
放大——提示词注入（prompt injection）本质上是把「注入」攻击面从数据层搬到了
**自然语言指令层**；而当模型被授予过多工具权限时，A01 的破坏力也成倍上升。阅读
`copilot-prompt-injection-rce` 与 `agentic-ai-threats` 两篇时，可与本表对照理解。
