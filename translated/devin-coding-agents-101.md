# 编码智能体 101：真正把事情做成的艺术

现在是 2025 年。编码智能体并非魔法，但它们已是我们所拥有的最接近魔法的东西。我们注意到一些工程师，尤其是高级到资深级别的工程师，比其他人更快地取得了成功。在此，我们分享一些源自我们客户和自身经验的顶级经验教训。

关于本指南：

## 产品无关

我们讨论的技巧将帮助你在使用任何编码智能体时取得成功。

## 注重实操

我们提供我们最喜爱的可操作建议。

## 面向技术

虽然编码智能体对许多人都有价值，但本指南是面向工程师编写的。

开发者工具一直在快速演进。十年前，是自动补全和智能感知（intellisense），能够建议方法名并执行程序化重构。四年前，是副驾驶（copilot）和 Tab 补全，能够为你写出接下来的几行代码。两年前，是生成式聊天机器人，能够协助你的开发并为你生成整个文件。而今天，是自主智能体，能够在极少人工干预的情况下，从初始描述一路做到最终的拉取请求（PR）。过去两年，我们通过构建 Devin 专注于实现这一愿景。如今，人们对自主智能体的兴趣达到了新的高度，尤其是随着同类产品[1] 除 Devin 外，近期发布的产品还包括 OpenAI 的 Codex 和 Google 的 Jules。一些本地智能体（如 Cursor 和 Claude Code）可以在并行工作区中运行，以达到类似的效果。的相继发布。这些智能体可以以多种形式出现，包括 Web 应用、移动应用，以及与 Slack、GitHub、Linear 和 Jira 等流行工具的集成。

虽然人类与 AI 助手搭档能比任何 AI 单独工作取得更多成就，但自主智能体端到端处理任务的能力带来了全新水平的多任务处理，让每位工程师都能成为工程管理者。

适应与这些新的 AI 同事高效协作可能需要一些时间。有趣的是，我们观察到高级到资深级别的工程师往往最快上手并熟练运用这些工具。最终，这些工具将在所有层级的工程岗位上普及。基于我们的经验和客户反馈，我们希望分享关键见解和经验教训，帮助每个人成功地将这些工具融入工作流程。

## 提示词基础

这些基本准则将帮助你在 2025 年高效地与编码智能体交互。即使其他什么都不记得，也至少要记住这些。

### 说明你想怎么做，而不只是做什么

把智能体想象成一个决策可能不可靠的初级编程伙伴。简单的任务可以直接描述，但对于更复杂的任务，要在一开始就清楚地说明你偏好的做法。提前向智能体提供整体架构和逻辑，不仅能提高其成功几率，还能减少你审查代码的时间，因为你已经熟悉预期的实现方式。

#### 示例：

不要只说"添加单元测试"，而要明确要测试的功能、指出重要的边界情况，并说明（如有需要）哪些部分需要模拟（mock）。

### 告诉智能体从哪里开始

想一想如果由你自己来处理这个任务，你会从哪里开始。即使你不知道具体的文件或函数名，也要提及相关的仓库、文档和涉及的关键组件。明确指出这些要素可以最大限度地减少白费力气和困惑。

#### 示例：

"请为我们的代码添加对 Google 模型的支持。你应该查阅[这里](link)的最新文档，并在模型组目录中创建一个新的实现文件。"

### 练习防御性提示

想象把同样的提示词交给一个新来的实习生。哪里可能会出现困惑或错误？预判这些点，并主动澄清你的指令，避免歧义。

#### 示例：

"请修复我们搜索模块的 C++ 绑定，以通过新的单元测试。注意，每次修改代码后，你可能都需要在测试前重新编译这些绑定。"

### 让智能体能够访问 CI、测试、类型检查和代码检查工具

智能体的许多魔力来自其修正自身错误并依据错误信息迭代的能力。通过类型检查器、代码检查工具（linter）和单元测试等工具提供强大的反馈循环，可以极大地提升其表现。比起普通 Python，考虑使用带类型的 Python；比起 JavaScript，考虑使用 TypeScript。教会你的智能体如何运行常见的检查和测试，确保它拥有所有必要的软件包和访问权限。如果智能体可以与浏览器交互，请提供运行前端开发环境的清晰说明。

#### 示例：

我们的团队从大部分无类型的 Python SDK 过渡到了全部带类型的 SDK（这也是一个非常适合交给编码智能体的任务）。

### 发挥你的专业经验

当你熟悉自己的代码库时，上述一切都会变得更容易。即便是简单的任务，也会因你验证逻辑和结果的能力而受益。人工监督仍然不可或缺——归根结底，代码最终的正确性由你负责。即使这些工具日益成熟，所有权和验证仍将是人类工程师的关键职责。

## 在工作流程中使用智能体

一旦掌握了与智能体沟通的基础，就该把这些 AI 助手带入日常工作流程了。以下是一些让智能体成为你日常工作一部分的实用方法：

### 立即接手新任务

想象一位同事给你发消息："嘿，我们能快速做个 X 吗？"或者"我们需要微调一下 Y。"与其让这些打断你的心流，不如直接给自主智能体发一个简短的提示词，让它去调查或进行修改。这样你就能专注于自己的主要任务。有了有趣的业余项目想法？需要快速制作原型、抓取数据或复现研究？交给你的智能体，稍后再回来查看。

#### 示例：

许多团队在讨论 Bug 修复或小的功能更新时，只需在 Slack 上 @Devin。

### 随时随地写代码

想象你在通勤或旅途中，突然出现一个紧急 Bug，或者你意识到自己可能在代码里留下了错误。别担心！自主智能体通常支持移动端访问，让你可以即时处理这些问题。无论是通过 Slack 的移动应用还是专用移动应用，许多智能体都能让你随时随地解决问题，即使你的 Wi-Fi 不太稳定。

#### 示例：

拥有这种灵活性让我们的团队在乘车和飞行途中高效了许多。

### 把杂活交给智能体

还在为二分查找旧提交或为新功能更新文档而烦恼吗？把这些重复性任务交给你的智能体吧。你将节省宝贵的时间，专注于更有创造性和影响力的工作。

#### 示例：

在我们的团队中，工程师发布一项改动后，让智能体更新所有相关文档和面向用户的文案，是很常见的做法。

### 摆脱分析瘫痪

纠结于一次重构是否真的能简化你的代码？在两种架构方案之间难以抉择？让你的智能体把两个方案都实现出来。有了具体的示例可供对比，决策就会变得简单直接，而且丢弃某个方案也不会伤害任何人的感情。

#### 示例：

在为文本框选择 Lexical 还是 Slate 时，我们让智能体分别实现了两个方案。最终 Slate 胜出，因为它交付了更好的最终效果。

### 设置预览部署

将你的 CI/CD 流水线设置为每有一个新 PR 就自动创建预览部署，为你提供一个即时可访问的 URL。在审查由 AI 智能体完成的前端任务时，这一点尤为方便。

#### 示例：

Vercel 是一个让预览部署变得超级简单的部署平台。

## 委派更大的工单

当你的拉取请求（PR）的规模和复杂度超出区区几个文件时，一次性完成就变得颇具挑战。然而，掌握如何委派中大型任务（通常是 1 到 6 小时的工作量），正是自主智能体带来最高回报的地方。你不仅能节省几分钟，还能夺回数小时的生产力。小任务可能毫不费力，但扩展智能体的能力去处理更大的任务，才能带来最大的收益。

### 自动化你的初稿

对于实质性的任务，使用自主智能体为你的 PR 创建初稿可以快速启动进展并大幅减少你的工作量。这里的成功取决于你提前清晰地传达期望的做法。把自己想象成指导初级开发者的架构师。清晰、详细的指令有助于避免花不必要的时间去纠正智能体代码中的根本性误解。

| 领域 | 起草 | 打磨 |
| --- | --- | --- |
| 新闻业 | 记者收集初始信息，撰写文章初稿 | 编辑审阅初稿、核查事实、润色并定稿发表。 |
| 餐厅 | 流水线厨师备料并制作初步菜品。 | 副厨添加调味料并调整菜品，使其味道更好，再端给食客。 |
| 编程 | 自主智能体根据初始计划开始任务，并创建第一版解决方案草稿 | 人类开发者审阅草稿 PR，给出反馈，并在合并前进行人工打磨 |

⚠️ 请记住，大型任务（目前还）无法完全放手。对于更具挑战性的任务，预期会有多轮反馈循环，并预计需要一些人工打磨。现实的目标是节省约 80% 的时间，而不是完全自动化；你的专业经验对于验证和最终质量保证仍然至关重要。

### 共同制定产品需求文档（PRD）

对于复杂或定义模糊的任务，与你的自主智能体合作制定详细计划会非常有效。如果你一开始并不了解每个细节或需求，完全没问题。可以先提示你的智能体探索一些发现性问题，例如"我们的认证系统是如何运作的？"或"哪些服务可能会受到影响？"你也可以让智能体找出具体的相关代码目标，供你尽早确认。

某些智能体（如 Devin 和 Claude Code）提供专门的规划模式，专注于阅读和探索现有代码，而不是立即修改。如果你希望在委派任务前做更充分的准备，像 deepwiki.com 和 Devin Search 这样的专用代码库搜索工具可以快速提供对代码库的洞察，帮助简化流程。

### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，要沿途设立明确的检查点：

计划 → 实现一部分 → 测试 → 修复 → 检查点审查 → 下一部分

明确要求在每个重要阶段之后暂停，尤其是对于跨多个层次（如数据库、后端、前端）构建的复杂功能。利用这些检查点确保实现符合你的预期，澄清疑问（例如"解释认证流程并确认其安全性"），并尽早纠正方向，避免问题级联扩散。

#### 示例：

"我希望你实现这个将跨越我们的数据库、后端和多个前端界面的功能。请先规划出所需的数据库模式（schema）变更，完成后告诉我，以便我执行迁移。" → "现在请实现后端改动，并添加测试以确保 XYZ 正常工作。完成后告诉我。" → "现在请在我们的 Web 和移动端界面中实现调用新后端接口的改动。"

### 教会它验证自己的工作

在给出反馈时，不要仅仅指出问题（"这个函数不能用"）。清楚地说明你的测试流程，使智能体能够独立验证未来的任务。对于你会经常重复的测试模式，将它们整合到智能体的永久知识库中（参见"添加到智能体的知识库"）。

#### 示例：

在 Devin 中，我们积极提示用户将重要的测试流程保存到智能体的持续记忆中，从而简化未来的交互。

### 提高 AI 热点区域的测试覆盖率

目前，智能体尚不能完全交互式地彻底测试所有场景。在 AI 大量修改的区域提高测试覆盖率，可以让你对智能体的输出更有信心。扎实的测试意味着，看起来正确的代码可以放心合并，无需担忧。

#### 示例：

在把实现从 Python 翻译成 C 的重任交给我们的 AI 之前，我们的团队加强了代码库中一个关键部分的单元测试。

## 自动化工作流程

智能体对传入事件的响应速度远快于人类，而且它们比人类同行更愿意做枯燥、重复的工作。

### 为最重复的工作创建快捷方式

工程团队经常会遇到重复的例行任务。这些正是交给智能体实现自动化的绝佳对象。常见的例子包括：

- 移除功能开关（feature flag）
- 升级依赖
- 在新功能的 PR 上修复和添加测试

为了高效地完成设置，经验丰富的工程师通常会创建一个健壮、可复用的提示词模板[2] 在 Devin 中，这些被称为剧本（playbook），可以在这些场景中反复运行。 。

#### 示例：

我们的一位客户每当开发新功能时，就会自动触发三个专门编写单元测试的智能体。

### 智能代码审查与执行

虽然已有专门用于快速代码审查的工具[3] 例如 Greptile 和 CodeRabbit ，但自主智能体可以成为一个有趣的选择，带来更准确的洞察，尤其是当它们已经为你的仓库功能建立了索引时。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把这份清单提交到代码库中。然后，与其编写传统的 lint 规则来捕获这些错误（这通常是不可能的），我们让一个智能体在每个新 PR 上运行，检查这些错误。

### 接入事故与告警

你还可以设置自主智能体，使其在特定事件发生时自动触发。例如，Devin 提供了可访问的应用程序接口（API），其他智能体可以通过命令行界面（CLI）命令集成到自定义工作流程中。这些设置与模型上下文协议（MCP）配合使用时效果尤佳，可以摄取第三方错误日志。

⚠️ 在处理生产环境服务中的问题分流（triage）时，AI 的调试能力并不那么出色。与其要求 AI 在问题出现时端到端地修复 Bug，通常更实际的做法是让 AI 只标记出最可疑的错误、变更等。

## 定制与性能提升

### 环境配置

没有什么比不完整或不匹配的环境更能拖慢智能体了。为了保持一切顺畅运行，要让智能体的配置与你的团队完全一致。这包括语言版本、软件包依赖和自动化检查。例如，应在智能体的环境中安装 pre-commit，并且环境配置（密钥、语言版本、虚拟环境、浏览器登录）应通过 .envrc 之类的工具或 .bashrc 的自定义配置自动加载。

### 构建自定义 CLI 工具和 MCP

MCP 随处可见，设置起来很快，可以快速尝试将你的智能体连接到外部工具[4] 在 Devin 中，MCP 仍处于测试阶段，我们正在摸索支持它们的最佳方式。如需使用，请联系我们！ 。但许多人忽视了为智能体设置简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，让它根据工单 ID 获取 Linear 工单的信息。你可能还想给智能体一个工具，让它可靠地执行工作流程中的常见环节，例如一个重启本地开发环境的脚本。

#### 示例：

我们有一位客户创建了一个 CLI 工具，只显示测试套件中第一个失败的测试，取得了很好的效果。该 CLI 会提示智能体只关注那个测试，并附上详细的错误信息，这让智能体在长任务上取得了更高的成功率和更快的完成速度。

### 添加到智能体的知识库

如果你的智能体犯了一些常见错误，那就是把你的反馈固化到智能体知识库中的好时机。在 Devin 中，有一个专门的知识管理系统。许多产品提供 .rules 文件、.md 文件，供智能体永久摄取。不要只给它关于你所使用框架的指南，还要告诉它项目的整体架构。告诉它不同类型的任务通常采用什么测试方式、如何运行重要命令，以及你推荐使用哪些工具。

## 自主智能体的局限性

### 调试能力有限

Bug 报告可能看起来简单得具有欺骗性。但许多 Bug 往往不仅需要访问数据库和日志，还需要超越当今大多数 AI 智能体的调试水平。如果使用 AI 辅助调试，我们建议让它列出一份可能根因的清单，而不是试图自行调试并修复一切。然后，人类可以根据自己的经验判断哪一个才是真正的根因。而一旦确定了原因，智能体在实施修复方面仍然相当得力。

### 细粒度视觉推理能力差

总的来说，当今模型不具备足够强的视觉推理能力，无法在细节层面匹配设计截图或 Figma 模型稿。它们最可靠的领域是可以在代码层面描述的视觉内容（例如给它 Figma 导出的代码）。如果你希望它匹配你的视觉风格，应该使用带有可复用组件的良好设计系统。

### 知识截断

每当你想使用一个新库时，都应该明确地为它指明最新文档。否则，由于预训练基座模型的知识截断，大多数智能体会默认采用这些库的旧模式。如果你为它指明文档，一个好的智能体可以克服这一点，但你必须对此保持警惕（记住，智能体甚至不知道这些库有新版本）。

实际考量

## 管理时间与减少损失

并非每次使用智能体都能取得成功。在 2025 年，这些智能体的产出确实存在一定的波动。这项工作的一部分内容，就是学会以某种方式使用智能体，从而最大化获得成功结果的几率，同时尽量减少浪费的时间和 Token。

### 愿意及早止损

初次使用智能体的人常犯的一个错误是，即使智能体的工作已经偏离正轨，他们仍执着于让这次交互成功。如果你发现自己心想"它无视我的指令"或"这东西在原地打转"，就应该果断终止那次对话或手动接管。发送更多消息更可能表明你的任务固有复杂度超出了智能体的能力，而不是某个可以纠正的简单错误。

### 分散你的试验

如果你是使用智能体的新手，我们建议一开始就分散下注。尝试各种不同的提示词和想法。在智能体天然表现良好的任务类型上加倍投入，而在它们表现不佳的任务上及时止损。不要觉得每次都必须强迫智能体取得成功。

### 没有进展时就重新开始

与人类相比，对智能体来说，重新开始往往是更正确的答案，而且频率要高得多。如果你给智能体布置了任务，而它难以处理反馈或纠正方向，那么用一个新智能体、在开头就给出全部指令重新开始，往往能更快取得成功。智能体修复一团糟环境的能力，远不如它从零开始写出全新代码的能力。

实际考量

## 安全与权限管理

### 为智能体创建账号

一次性邮箱有助于安全地测试网站。如果智能体需要访问云资源，请为其创建自定义的 IAM 角色。

### 给它开发/预发布环境

理想情况下，智能体应使用与你团队工程师相同的测试配置。我们建议完全避免赋予其生产环境服务的访问权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，只给它只读访问权限。我们发现，任何与外部服务交互的脚本，仍由人类手动运行会更有帮助。

我们坚信软件工程师不会消失。即使编码智能体变得越来越聪明、越来越能干，深厚的技术专长和对代码库的深入了解仍然弥足珍贵。如今，对你自己的项目、系统和代码的真正所有权比以往任何时候都更加关键。在我们当下的团队中，工程师既要负责监管多个系统，又要保持深刻的理解和审慎的判断。随着自动化放大你的影响力，并行处理多个任务的能力将不再只是可能，而将成为必需。我们很兴奋地分享我们在为自己组织迎接这一转变时所积累的见解，让你和你的团队也能在不断演进的软件开发世界中蓬勃发展。
