# 精读笔记：Traces 与 Spans——你应当了解的可观测性基础

> 原文：Traces & Spans: Observability Basics You Should Know（Last9）
> ⚠️ 本笔记为**提炼与讲解**，非逐段译文。原文含厂商产品推广内容（Last9 自家产品），
>    已在下文标注并剔除，纯概念部分为业界通用知识。

## 一句话结论

**Trace（追踪）是请求的完整故事，Span（跨度）是故事中的一项工作单元。**
在微服务架构中，它们是定位「哪个服务慢了」的唯一有效手段。

## 核心概念

| 概念 | 定义 |
|---|---|
| **Trace** | 记录一个请求在分布式系统中**完整旅程**——从用户点击按钮到看到结果 |
| **Span** | 该旅程中的一个**工作单元**——一次数据库查询、一次 API 调用、一次函数执行 |
| **关系** | 一个 trace 包含多个 span；span 可**嵌套**以表达父子关系 |

原文给出的结构示意：

```
Trace
├── Span (API Gateway)
│   ├── Span (Auth Service)
│   ├── Span (User Service)
│   └── Span (Database Query)
└── Span (Response Formatting)
```

### Span 携带的数据

Span 不只是时间戳，它包含：

- **Name**：这个 span 代表什么操作
- **Timing**：开始与结束时间
- **Status**：成功 / 错误等
- **Attributes**：自定义键值对（如 `user_id`、`cart_size`）
- **Events**：span 内的值得注意的事件
- **Links**：到其他 span 的连接

## 为什么重要（DevOps 视角）

场景：运行着几十个微服务，用户报告**结账流程很慢**。

| 没有 tracing | 有 tracing |
|---|---|
| 只能逐个服务排查，浪费宝贵时间 | **立即定位瓶颈**：看清是哪个服务或函数耗时过长 |
| 难以跨服务边界调试 | 跟随请求在服务间跳转 |
| 依赖关系靠猜 | **可视化**服务如何连接与依赖 |
| 性能优化靠试错 | 精准识别并修复慢操作 |
| MTTR 长 | **缩短平均恢复时间**，更快到达根因 |

## 技术实现要点

### 1. 上下文传播（Context Propagation）

要让追踪跨服务边界生效，每个服务需要知道自己在处理**同一个请求的一部分**。
实现方式是在服务间传递 **trace ID 与 span ID**：

- 请求首次进入系统时被分配唯一的 trace ID
- 该 ID 随请求在服务间流转（通常放在 **HTTP 头**中）
- 每个服务创建自己的 span，但**链接到同一个 trace**

### 2. 采样策略（Sampling）

全量追踪会产生海量数据，因此多数系统采用采样。原文列出三种策略：

| 策略 | 说明 |
|---|---|
| **Head-based**（头部采样） | 在请求**开始时**决定是否采样 |
| **Tail-based**（尾部采样） | 在请求**完成后**决定——**更适合捕获错误** |
| **Priority**（优先级采样） | 重要操作始终追踪，常规操作才采样 |

> **对 AI 智能体值班场景的启示**：错误的追踪绝不能被采样掉——**尾部采样是
> 智能体事后复盘事故时最需要的策略**。

- 流行框架的自动埋点
- 统一的采集与导出方式

## 进阶技巧

### 分布式上下文管理

复杂系统中不只管理 trace ID。**W3C Trace Context 规范**提供：

- `traceparent`：包含 trace ID 与父 span ID
- `tracestate`：允许厂商添加自定义上下文数据

使用这些头可确保追踪**跨服务、跨厂商**可用。

### 关联 Trace、指标与日志

可观测性的真正威力来自**连接不同信号**：

- **Exemplar traces**：把指标链接到产生它们的追踪
- **日志中的 trace ID**：加入 trace ID 以便交叉引用
- **自定义 attributes**：在所有遥测类型间保持一致的属性

### 错误处理与异常追踪

- 用错误状态标记 span
- 记录带堆栈的异常
- 添加事件展示错误演进过程
- 创建 **baggage** 携带错误上下文跨服务边界

## 实践模式与反模式

**✅ 有效模式**

| 模式 | 说明 |
|---|---|
| 有意义的 span 名 | 统一命名规范，如 `service_name/operation` |
| 恰当的粒度 | 为**重要操作**建 span，而非每个函数调用 |
| 正确传播上下文 | 确保上下文流经所有通信通道 |
| 有用的属性 | 加 `user_id`、特性开关等有助于排障的属性 |
| 性能意识 | 警惕过多 span 创建带来的开销 |

**❌ 应避免的反模式**

| 反模式 | 后果 |
|---|---|
| **过度埋点** | 过多 span 引发性能问题 |
| **上下文缺失** | 传播失败导致追踪跨服务断裂 |
| **命名不一致** | 不同命名规范使追踪难以解读 |
| **数据过多** | 在 span 中放大 payload，压垮追踪后端 |
| **忽略第三方服务** | 外部调用的 span 缺失造成盲区 |

## 业务价值（超越技术）

追踪不只是排障工具，还能支撑业务决策：

- 端到端跟踪关键**用户旅程**
- 度量关键**业务操作**的性能
- 基于追踪数据设定 **SLO（服务等级目标）**
- **用真实用户口径量化性能问题的成本**
- 通过给 span 添加业务属性建立**业务上下文**

> 当你能展示技术改进如何影响用户体验与业务指标时，**你在 DevOps 与业务相关方
> 之间架起了桥梁**。

## FAQ 要点

| 问题 | 答案 |
|---|---|
| **追踪 vs 日志** | 日志记录离散事件；追踪展示跨服务的操作关系。**日志告诉你发生了什么，追踪告诉你它是怎么发生的** |
| **加了追踪会拖慢应用吗** | 现代追踪库开销很小，**配置得当时通常 < 3%**；配合采样可进一步降低 |
| **必须改所有代码吗** | 不必。多数框架提供自动埋点，OpenTelemetry 对主流语言均有支持 |
| **数据量多大** | 差异极大，繁忙系统**每天数 GB 到数 TB**——这正是选型要考虑成本的原因 |
| **能用于安全与合规吗** | 能。**追踪形成请求流转的审计轨迹**；配合属性可追踪哪些用户/服务在何时访问了什么数据 |
