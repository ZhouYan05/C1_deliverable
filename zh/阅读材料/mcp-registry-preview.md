# MCP 注册中心正式推出 | 模型上下文协议博客

> 原文标题：Introducing the MCP Registry
> 授权：MCP 开放源码项目，采用宽松许可

今天，我们正式推出模型上下文协议（MCP）注册中心（MCP Registry）——这是一个面向
公开可用 MCP 服务器的开放目录与 API，用于提升其可发现性与可实现性。通过标准化
服务器的发布与发现方式，我们既扩大了服务器的触达范围，也让客户端更容易完成连接。

MCP 注册中心现已开放预览。要开始使用：

- **服务器维护者**：参照《将服务器添加到 MCP 注册中心》指南添加你的服务器
- **客户端维护者**：参照《访问 MCP 注册中心数据》指南获取服务器数据

## MCP 服务器的唯一事实来源

2025 年 3 月，我们曾表示希望为 MCP 生态构建一个中央注册中心。今天我们宣布：
`https://registry.modelcontextprotocol.io` 已作为官方 MCP 注册中心上线。作为 MCP
项目的一部分，MCP 注册中心以及其上层 OpenAPI 规范均为开源——这意味着任何人都可以
构建与之兼容的子注册中心。

我们的目标是标准化服务器的发布与发现方式，提供一个首要事实来源（primary source of
truth），供各类子注册中心在其之上构建。进而，这能扩大服务器的触达范围，并帮助客户端
在整个 MCP 生态中更轻松地找到所需服务器。

### 公共与私有子注册中心

在构建中央注册中心的过程中，对我们而言很重要的一点是：**不削弱社区与企业已经建好的
既有注册中心**。MCP 注册中心充当公开可用 MCP 服务器的首要事实来源，而各组织可以
根据自定义标准创建自己的子注册中心。例如：

**公共子注册中心**：例如与各个 MCP 客户端绑定的、带强烈主观取向的「MCP 市场」，
可以自由地增补、增强它们从上游 MCP 注册中心摄取的数据。每类 MCP 最终用户的需求都
不同，如何以贴合自身取向的方式服务好终端用户，正是各 MCP 客户端市场应尽的职责。

**私有子注册中心**：存在于有严格隐私与安全要求的企业内部；但 MCP 注册中心为这些企业
提供了一个可供构建的上游数据源。最低限度上，我们的目标是与这些私有实现共享 API
模式（schema），以便相关 SDK 与工具能在整个生态中被共享。

在两种情形下，MCP 注册中心都是**起点**——它是 MCP 服务器维护者发布并维护其自行上报
信息的集中位置，下游消费者可以在此基础上加工并交付给各自的最终用户。

### 社区驱动的治理机制

MCP 注册中心是 MCP 官方项目，由注册中心工作组维护，采用宽松许可。社区成员可以提交
issue，标记违反 MCP 治理准则的服务器——例如含有垃圾内容、恶意代码，或冒充合法服务的
服务器。注册中心维护者随后可以把这些条目加入拒绝名单（denylist），并追溯性地将其从
公开访问中移除。

## 快速上手

要开始使用：

- **服务器维护者**：参照《将服务器添加到 MCP 注册中心》指南添加你的服务器
- **客户端维护者**：参照《访问 MCP 注册中心数据》指南获取服务器数据

本次 MCP 注册中心预览版的目的，是在正式可用（GA）之前改进用户体验，**不提供数据持久性
保证或其他任何担保**。我们建议 MCP 采用方密切关注开发进展：在注册中心正式可用之前，
可能会发生破坏性变更（breaking change）。

随着注册中心持续开发，我们欢迎在 `modelcontextprotocol/registry` GitHub 仓库反馈与
贡献：讨论、issue 与 pull request 均受到欢迎。

**本节要点**

- 注册中心解决的是 MCP 服务器「**发现难**」这一老问题：此前服务器只能靠用户手工抄
  URL，生态碎片化严重。
- 采用**开放上游 + 可自定义子注册中心**的联邦式设计，官方不与社区/厂商自建市场竞争。
- 治理靠**社区举报 + 维护者拒绝名单**，而非事前审核——降低中心化瓶颈。
- 处于预览期，**接口可能破坏性变更**，生产接入需锁版本。
