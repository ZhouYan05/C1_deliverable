# 精读笔记：规格已死，规格万岁！

> 原文：The spec is dead, long live the spec!
> 作者：Ravi Mehta、Danny Martinez（2025-07-31）
> 副标题：原型成了新规格，而规格成了新的……源代码？
> ⚠️ 本笔记为**提炼与讲解**，非逐段译文。原文版权归作者所有。

## 一句话结论

**在 AI 时代，规格（spec）不再是官僚文书，而是新的源代码。** 代码是规格的「有损投影」，
把代码留下、把提示词扔掉，等于「撕掉源文件，然后小心翼翼地给二进制做版本控制」。

## 论点一：PM 突然成了瓶颈

作者观察到规格文档在职业生涯中**越来越短**：

- 刚进微软时，PM 的价值以其规格文档的**厚度**衡量
- 到 Tripadvisor 时，公司开始神化那些能带着「餐巾纸规格」去产品评审会的 PM

而产品团队普遍把规格当**文书工作**——发布前的必要之恶。工程师因优雅的代码被赞颂，
设计师因漂亮的 UX 被赞颂，PM 因交付影响而受肯定，但**规格本身总被草草带过、扔掉、遗忘**。

作者反驳：在他编写的《Product Competency Toolkit》中，**功能规格（Feature Specification）
高居十二项能力之首**——它是产品执行的基础。

> **「无瑕的执行是好产品管理的根基，而一份好规格就是起跑线。」**

**关键转折**：工程师正在变得**快得多**——AI 能在几分钟内把粗糙想法变成可运行代码。
瓶颈不再是怎么构建，而是**知道该构建什么，并让团队围绕这些需求对齐**。

于是那份不起眼的规格**从临时文书变成了产品管理的基础，它本身正在成为源代码**。

### 佐证：吴恩达的观察

在《Building Faster with AI》演讲中，吴恩达指出一个前所未有的趋势：

> 「我职业生涯中第一次看到有人向我提议**配备两倍于工程师数量的 PM**。我仍然不知道这是
> 不是个好主意，但我认为这是世界走向的一个信号。」

> **这验证了作者此前的预测：随着工程师借助 AI 交付速度快数倍，公司需要的是
> _更多_ PM 来支撑这些高产的工程师，而不是更少。**

## 论点二：规格是新的源代码

### 传统开发的类比

在传统软件开发中，程序员编写人类可读的**源代码**，编译成高度优化的机器可读**目标代码**。
目标代码（也叫二进制）是**可由源代码重建的副产品**——源代码才是真正的事实来源。

### OpenAI 的 Sean Grove 提出的论点

在演讲《The New Code》中，OpenAI 的 Sean Grove 提出一个颇具挑衅性的主张：
**一份写得好的提示词（即规格）就是新的源代码。**

### 现状：我们把 AI 开发做反了

按这个视角看，**我们今天的 AI 开发流程是颠倒的**：

```
我们精心撰写提示词 → 把意图传达给模型 → AI 生成代码 → 保留代码，扔掉提示词
```

Grove 的评论：

> **「这感觉就像你把源文件撕碎了，然后非常小心地对二进制做版本控制。」**

传统编程中源代码是神圣的——它包含注释、结构与文档，是理解与修改系统所需的全部。
二进制只是下游产物。**但在 AI 时代，我们把这段关系翻转了**：把生成的代码当成值得
保留的产物，把规格（提示词）当成一次性的。

### 为什么代码是「有损的」

Grove 认为代码——**即便优雅的代码**——是规格的**有损投影（lossy projection）**：

- 就像反编译二进制文件无法还原原始注释与变量名，**阅读代码也无法告诉你它背后的完整意图**。
- 而规格**包含全部信息**。一份足够稳健的规格可以生成：

> 「**好的 TypeScript、好的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。**」
> ——Sean Grove，OpenAI

### 规格能做而代码做不到的事

> **规格能让人与机器在共同目标上对齐。**

> 「一份书面的规格能有效地让人对齐，它是用来沟通、讨论、辩论、引用和对齐的载体。」
> ——Sean Grove

> 「**在不久的将来，最善于沟通的人就是最有价值的程序员。事实上，如果你能有效地沟通，
> 你就能编程。**」

> **新的稀缺技能不是编码，而是写出完整捕获意图与价值观的规格。**

对 PM 来说这应该很熟悉——**这本就是我们一直在做的事，只不过现在机器也在听了**。

## 论点三：那原型不是把规格杀了吗？

### 旧工作流

产品生命周期曾**必须从规格开始**（规格/PRD/概念文档/餐巾纸），以此启动线框图、设计、
原型与 MVP 开发。

工程师搭出基础 MVP，只为让**点什么**先到用户手里。「如果你不为产品的第一版感到难堪，
那你发布得太晚了」成了信条。

```
模糊想法 → 线框图 → 设计稿 → 工程师搭 MVP → 客户反馈 →
痛苦地改规格 → 线框图 → 设计稿 → 重建 → 祈祷
```

### 新工作流

如今**不需要写一行代码**就能把原型交到客户手上。v0、Lovable、Replit 这类工具让你
**几小时（而非几周）**做出可运行原型，**无需工程介入**。

持有一个「vibe code 出来的」原型后，你可以**在写任何一行功能规格之前**就收集到
真实客户反馈——检验假设、迭代流程、打磨交互。

```
模糊想法 → 快速原型 → 客户反馈 →  crystal-clear 规格 → AI 辅助实现
```

> **「原型没有杀死规格，而是在让规格变得更好。」**

## 案例：规格驱动开发实战

**Danny Martinez** 是 decimals（一个隐身中的平台）的创始人，该平台帮助创作者经济中的
专家把自己网络中的人才安排到工作中。这套规格驱动流程带来两个实际效果：

1. 大型功能与工程团队的沟通**大幅改善**
2. 让**毫无编码经验**的 Danny 也能把小功能从详细规格一路做到上线

### 一个具体例子

新落地页上线后，需要给专家们一个快速访问自己页面链接的方式。Danny 的联合创始人
在 Slack 上说：

> 「我们需要在 header 加一个按钮，指向 company-apply 页面。我现在在弄邮件。这个如果
> 你能接手的话，属于 vibe code-able 的活儿。」

**技术栈**：项目管理 Linear · IDE VS Code · 扩展 GitHub Copilot Pro · 模型 Claude Sonnet 4
· MCP 服务器 Linear MCP server（让 Copilot 能访问 Linear 工单）

**上线步骤**（几分钟内完成）：

1. 从联合创始人的 Slack 消息**生成一个 Linear 工单**
2. 在工单里**澄清新文案的具体内容**
3. 打开 Copilot，提示 Claude **打开该 Linear 工单**
4. 提示 Claude **审阅工单并结合代码库分析**
5. 提示 Claude **创建分支并实现这些改动**
6. **测试**改动是否符合预期
7. 在 GitHub 上**开 PR** 合入代码库
8. 等待工程师**审查/批准** PR

> **放大来看，这套配置真正的力量才显现出来**：是的，例子很琐碎，但要点成立——
> **一个非技术人员现在可以在 Linear 工单、代码库与工程师之间往返，全程只靠几个提示词。**

### 生效的前提条件（作者诚实的补充）

- **具体性**：含糊的规格只会带来混乱的代码库。用 Claude 把工单初稿细化、审阅代码库、
  帮助写得更具体，是流程中**不可或缺的一环**。他们还有专门的好规格撰写指南。
- **选择性**：上述做法**适合简单任务**。工单越复杂，越需要懂行的人介入
  （在这些情况下「自助」往往名不副实）。
- **守门（Gatekeeping）**：这套做法之所以有效，是因为**确实有一位懂行的工程师**在
  审查改动、把握简洁性与功能性之间的平衡。

> **但规则确实变了：规格是所有产品构建者——包括 LLM——的事实来源。**

> 「配置得当的话，**非技术人员为代码库做贡献完全现实**。花足够的时间和耐心，你可以
> 开始理解代码库并自己实现改动，而不是每次都指望 Claude 救场。」

> 「总有一天，你甚至可能预期一个 AI 智能体在你喝咖啡时就把你的工单发布了。」

## 结语：吉布森定律

科幻作家 William Gibson（"cyberspace" 一词的创造者）曾说：

> **「未来已经到来——只是它还没有均匀地分布。」**

作者用这句话描述 AI 的现状：**AI 的收益极不均匀**。

| 以 **AI 速度** 运转 | 仍以**人类速度** 运转 |
|---|---|
| 生成代码 | 与客户交谈 |
| 生成文本 | 发现他们的需求 |
| 生成图像 | 说服他们购买 |

这种不均匀正在**重塑产品团队**：聚光灯正从「实现工作」转向「理解工作」。
那些一直让优秀 PM 与众不同的核心技能——**理解用户需求、清晰定义问题、设计优雅解法**——
变得**呈指数级地更有价值**。

> **优秀的 PM 把这些洞见转化为规格——对齐团队、指导实现，并在日益自动化的开发世界中
> 成为**持久存在的核心产物**。

- 与 `how-long-contexts-fail` 呼应：规格之所以重要，正因为它是**对抗上下文污染与冲突

- 与 `writing-effective-tools-for-agents` 呼应：那份文章说「像给新同事讲工具那样写工具
  描述」，本文说「像写规格那样写提示词」——**同一个道理的两个场景**。

## 可迁移到实践的三条

1. **保留提示词，像保留源代码一样。** 生成代码的同时把规格一起版本化。
2. **用原型前置验证假设**，让规格的输入质量提高，而不是在模糊需求上直接生成代码。
3. **规格是给人看的，不是给机器喂的**——但现在机器也在读，所以它必须同时对齐人和模型。
