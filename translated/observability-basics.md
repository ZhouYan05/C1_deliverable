# 链路追踪（Trace）与跨度（Span）：你需要了解的可观测性基础 | Last9

在现代软件架构中，应用不仅变得越来越大——而且越来越分布式。随着微服务、无服务器函数和容器在多个环境中运行，想要了解系统内部发生了什么，就像试图在暴风雨中追踪一滴雨水。

这正是链路追踪和跨度派上用场的地方。这些可观测性工具不只是流行词——它们是你理解复杂分布式系统的秘密武器。下面我们来拆解一下链路追踪和跨度是什么、为什么重要，以及如何利用它们更快地进行故障排查、构建更可靠的系统。

## 理解链路追踪与跨度：核心概念

链路追踪记录请求在分布式系统中流转的旅程。可以把一条链路追踪想象成一个请求从始至终的完整故事——从用户点击按钮的那一刻起，直到他们看到结果为止。

跨度是链路追踪的基本构件。每个跨度代表这段旅程中的一个工作单元——比如一次数据库查询、一次 API 调用或一次函数执行。跨度彼此嵌套，展示操作之间的父子关系。

简单来说，二者的关系如下：

- 一条链路追踪包含多个跨度
- 每个跨度代表一个操作
- 跨度包含时间数据和元数据
- 跨度可以嵌套，以展示操作之间的相互关系

```
Trace
├── 跨度（API 网关）
│   ├── 跨度（认证服务）
│   ├── 跨度（用户服务）
│   └── 跨度（数据库查询）
└── 跨度（响应格式化）
```

## 链路追踪与跨度为 DevOps 从业者带来的好处

你正在运行一个由几十个微服务组成的复杂系统。突然，用户反馈结账流程变慢了。如果没有链路追踪，你就得逐个检查每个服务，浪费宝贵的时间。

借助链路追踪和跨度，你可以：

- 即时定位瓶颈：准确看到哪个服务或函数耗时过长
- 跨服务边界调试：跟随请求在服务之间跳转的路径
- 理解依赖关系：直观展示服务之间如何连接、如何相互依赖
- 提升性能：精准识别并修复慢操作
- 缩短平均恢复时间（MTTR）：问题出现时更快定位根本原因

## 链路追踪与跨度的技术实现

下面我们深入了解一下链路追踪在分布式系统中的工作原理。

### 链路追踪上下文与传播

要让链路追踪跨服务边界生效，每个服务都需要知道自己在处理同一个请求的一部分。这需要通过上下文传播来实现——即在服务之间传递追踪 ID 和跨度 ID。

当请求首次进入你的系统时，它会被分配一个唯一的追踪 ID。当请求在服务之间流转时，这个 ID 会随请求一起传递（通常通过 HTTP 请求头）。随后，每个服务创建自己的跨度，但都将它们链接到同一条链路追踪上。

### 跨度属性与事件

跨度不只是时间戳——它们承载着丰富的数据：

- 名称：该跨度代表什么操作
- 时间：开始和结束时间
- 状态：成功、错误等
- 属性：自定义键值对（例如 user_id 或 cart_size）
- 事件：跨度内值得注意的事件
- 链接：与其他跨度的关联

### 采样策略

对一切都进行追踪会产生海量数据。因此大多数系统都会采用采样——只收集一定比例的链路追踪。聪明的采样策略包括：

- 头部采样：在请求开始时决定是否采样
- 尾部采样：在请求完成后决定（更适合捕获错误）
- 优先级采样：始终追踪重要操作，对常规操作进行采样

### 在你的代码中实施链路追踪

下面是一个使用 OpenTelemetry 在 Node.js 应用中创建跨度的简化示例：

```
// Initialize the OpenTelemetry SDK (once in your app)
const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { SimpleSpanProcessor } = require('@opentelemetry/sdk-trace-base');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const provider = new NodeTracerProvider();
const exporter = new OTLPTraceExporter({
 url: 'http://localhost:4318/v1/traces',
});
provider.addSpanProcessor(new SimpleSpanProcessor(exporter));
provider.register();

// Get a tracer
const { trace } = require('@opentelemetry/api');
const tracer = trace.getTracer('my-service');

// Create spans in your code
async function processOrder(orderId) {
 const span = tracer.startSpan('process-order');
 
 // Add attributes to the span
 span.setAttribute('order.id', orderId);
 span.setAttribute('customer.type', 'premium');
 
 try {
 // Do work...
 
 // Create a child span
 const dbSpan = tracer.startSpan('database-query', {
 parent: span,
 });
 
 try {
 // Run database query...
 dbSpan.end();
 } catch (error) {
 dbSpan.setStatus({ code: SpanStatusCode.ERROR });
 dbSpan.recordException(error);
 dbSpan.end();
 throw error;
 }
 
 span.end();
 } catch (error) {
 span.setStatus({ code: SpanStatusCode.ERROR });
 span.recordException(error);
 span.end();
 throw error;
 }
}
```

## 高级链路追踪技巧

基础链路追踪就位之后，这些高级技巧能让你的可观测性更上一层楼。

### 分布式上下文管理

在复杂系统中，你需要管理的上下文远不止追踪 ID。W3C Trace Context 规范为以下内容提供了标准：

- traceparent：包含追踪 ID 和父跨度 ID
- tracestate：允许供应商添加自定义上下文数据

使用这些请求头可以确保你的链路追踪在不同的服务和供应商之间正常工作。

### 链路追踪、指标与日志的关联

可观测性的真正威力来自于将不同的信号关联起来：

- Exemplar 链路追踪：将指标与产生这些指标的链路追踪关联起来
- 日志中的追踪 ID：在日志消息中加入追踪 ID，便于交叉引用
- 自定义属性：在所有遥测数据类型中使用一致的属性

### 错误处理与异常追踪

当异常发生时，跨度可以提供关键的上下文信息：

- 将跨度标记为错误状态
- 记录异常及其堆栈跟踪
- 向跨度添加事件，展示错误的发展过程
- 创建 Baggage 项，跨服务边界传递错误上下文

## 实战中的链路追踪模式与反模式

### 有效的链路追踪模式

- **有意义的跨度命名**：使用一致的命名规范，例如 service_name/operation
- **合适的粒度**：只为重要操作创建跨度，而不是每个函数调用都创建
- **正确的上下文传播**：确保链路追踪上下文流经所有通信渠道
- **有用的属性**：添加有助于故障排查的属性，例如用户 ID 或功能开关
- **关注性能**：警惕过度创建跨度带来的开销

### 需要避免的链路追踪反模式

- **过度埋点**：创建过多的跨度会导致性能问题
- **上下文缺失**：未能传播上下文会破坏跨服务边界的链路追踪
- **命名不一致**：使用不同的命名标准会让链路追踪更难解读
- **数据过多**：在跨度中放入大型负载会压垮你的链路追踪后端
- **忽视第三方服务**：外部调用缺少跨度会造成盲区

## 常见问题（FAQ）

### 链路追踪和日志记录有什么区别？

日志记录捕获离散的事件，而链路追踪展示跨服务操作之间的关系。日志告诉你发生了什么，链路追踪展示事情是如何发生的。

### 添加链路追踪会拖慢我的应用吗？

现代链路追踪库的开销极小——正确配置时对性能的影响通常低于 3%。通过采样，你还可以进一步降低这种影响。

### 我需要修改所有代码才能添加链路追踪吗？

不一定。许多框架提供自动埋点，只需极少的代码改动即可添加链路追踪。OpenTelemetry 为大多数语言中的流行框架提供了自动埋点能力。

### 分布式链路追踪会产生多少数据？

这因流量、采样率和跨度细节的不同而差异很大。对于繁忙的系统，每天的数据量可能从 GB 级到 TB 级不等。这就是为什么选择合适的可观测性平台对成本控制至关重要。

### 链路追踪对安全和合规有帮助吗？

当然！链路追踪会为系统中的请求流转创建审计记录。借助合适的属性，你可以追踪哪些用户或服务在何时访问了哪些数据。

### 链路追踪和跨度如何与其他可观测性信号配合？

链路追踪与指标和日志互为补充。指标从高层次展示系统健康状况，日志提供详细的事件，而链路追踪则把这些点串联起来，展示请求在服务之间的流转情况。
