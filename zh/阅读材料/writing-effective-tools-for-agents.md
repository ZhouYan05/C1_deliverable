# 为 AI 智能体编写高效工具 —— 用 AI 智能体来写工具

> 原文：Writing effective tools for AI agents—using AI agents
> 作者：Ken Aizawa 及 Anthropic 研究团队
> 授权：Anthropic 官方工程博客，允许翻译，需署名并回链原文

模型上下文协议（MCP）可以让 LLM 智能体配备上百种工具以解决现实任务。但我们该怎样
让这些工具发挥最大效能？

本文介绍了我们在多种智能体式 AI 系统中提升性能的最有效技术，内容涵盖：

- 如何为你的工具构建并测试原型
- 如何创建并运行全面的工具评测（evaluation）
- 如何与 Claude Code 等智能体协作，自动提升工具性能

最后我们总结出若干编写高质量工具的关键原则：

- 选择正确的工具来实现（以及不去实现）
- 为工具做命名空间划分，界定清晰的功能边界
- 从工具向智能体返回有意义的上下文
- 面向 token 效率优化工具响应
- 对工具描述与规格做提示词工程

构建评测能让你系统性地度量工具性能；你还可以用 Claude Code 针对该评测自动优化工具。

---

## 什么是「工具」？

在计算领域，**确定性系统**给定相同输入每次都会产生相同输出；而**非确定性系统**
——比如智能体——即使起始条件相同，也可能生成有差异的响应。

传统上我们写软件，是在**确定性系统之间**建立契约。例如 `getWeather("NYC")` 这样的
函数调用，每次都会以完全相同的方式取回纽约市的天气。

而**工具**是一种全新的软件，它体现的是**确定性系统与非确定性智能体之间**的契约。
当用户问「我今天该带伞吗？」时，智能体可能会调用天气工具、依据通用知识直接回答，
甚至可能先反问一句地点。有时它还会产生幻觉，甚至根本没搞懂该怎么用这个工具。

这意味着我们必须从根本上重新思考为智能体编写软件的方式：不能再按给其他开发者或
系统写函数、写 API 的惯常做法来写工具和 MCP 服务器，而是要**为智能体而设计**。

我们的目标是扩大智能体能够有效发挥的「作用面」——让它们借助工具探索多种可行的
成功策略。所幸根据我们的经验，对智能体最「合手（ergonomic）」的工具，对人类来说
也往往出人意料地直观易懂。

## 如何编写工具

本节说明如何与智能体协作，编写并改进交给它们的工具。先为工具搭一个快速原型并在
本地测试；接着运行一次全面评测以度量后续改动。与智能体协同工作，你可以反复执行
「评测 → 改进」这一循环，直到智能体在现实任务上表现强劲。

### 构建原型

不亲手上手，很难预判哪些工具对智能体「合手」、哪些不合适。先把工具原型搭起来。
如果你用 Claude Code 来写工具（可能是一次性生成），**务必把工具所依赖的软件库、
API 或 SDK 的文档提供给 Claude**（包括可能的 MCP SDK）。对 LLM 友好的文档通常能在
官方文档站点的扁平化 `llms.txt` 文件中找到。

把工具包装成本地 MCP 服务器或桌面扩展（DXT），即可在 Claude Code 或 Claude 桌面
应用中连接并测试。

```bash
# 把本地 MCP 服务器接入 Claude Code
claude mcp add <name> <command> [args...]
```

接入 Claude 桌面应用：分别前往 **设置 > 开发者** 或 **设置 > 扩展**。

工具也可以直接传入 Anthropic API 调用做程序化测试。

**自己动手测一遍工具**，找出粗糙之处（rough edges）。向用户收集反馈，建立直觉，
判断你的工具应当支撑哪些用例与提示词。

### 运行评测

接下来通过运行评测来度量 Claude 使用你工具的效果。先基于真实世界用例**生成大量评测
任务**。我们建议与智能体协作分析结果、判断如何改进工具。

**生成评测任务**

有了早期原型，Claude Code 可以快速探索你的工具并创建数十组「提示—响应」对。
提示应源自真实用例，并基于真实的数据源与服务（例如内部知识库和微服务）。我们建议
避免过于简单、表面的「沙箱」环境——它们无法以足够的复杂度压测你的工具。**高强度的
评测任务可能需要多次工具调用，甚至数十次。**

高质量任务示例：

- 与 Jane 安排下周会议讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的纪要，并预订一间会议室。
- 客户 ID 9182 报告称一次购买尝试被重复扣款三次。找出所有相关日志条目，并判断是否还有其他客户受同一问题影响。
- 客户 Sarah Chen 刚提交了取消请求。准备一份挽留方案，并判断：(1) 他们为什么要离开；(2) 什么样的挽留方案最有吸引力；(3) 在给出方案之前我们应注意哪些风险因素。

质量较弱的任务（**不推荐**）：

- 与 jane@acme.corp 安排下周会议。
- 在支付日志中搜索 purchase_complete 和 customer_id=9182。
- 查找客户 ID 45892 的取消请求。

每条评测提示都应配一个**可验证的响应或结果**。验证器可以简单到对标准答案与采样响应
做精确字符串比对，也可以高级到委托 Claude 来评判。要**避免过于严苛的验证器**——
因格式、标点或同样正确的替代措辞等表面差异而误判正确答案。

你还可以为每组「提示—响应」指定你预期智能体调用的工具，用来度量智能体是否真正
理解了每个工具的用途。但因为正确解法往往有多条路径，尽量不要过度指定或过拟合到
某一种策略。

**运行评测**

我们建议用直接的 LLM API 调用以程序化方式运行评测。使用简单的智能体循环
（交替执行 LLM API 调用与工具调用的 while 循环）：每个评测任务一个循环。每个评测
智能体只接收一条任务提示与你的工具。

在评测智能体的系统提示中，我们建议**同时要求输出结构化响应块（用于验证）、推理块
与反馈块**。要求智能体在工具调用块与响应块之前先输出推理，可通过触发思维链（CoT）
行为提升 LLM 的有效智能水平。

若用 Claude 运行评测，可直接开启**交错思考（interleaved thinking）**获得类似能力。
这有助于你探究智能体为何调用或不调用某些工具，并凸显工具描述与规格中需要改进之处。

除顶层准确率外，我们还建议采集这些指标：**单次工具调用与任务的总耗时**、**工具调用
总次数**、**总 token 消耗**、**工具错误数**。追踪工具调用能揭示智能体偏好的常见工作流，
也为工具整合创造机会。

**分析结果**

智能体是发现问题的得力伙伴——从互相矛盾的工具描述，到低效的工具实现、令人困惑的
工具模式，它都能给出反馈。但请记住：**智能体在反馈和响应中「没有说」的，往往比
「说了的」更重要。大模型并不总是言其所想。**

- 观察智能体在哪里卡住、困惑。
- 通读评测智能体的推理与反馈（或 CoT），识别粗糙之处。
- 复查原始记录（transcript），包括工具调用与工具响应，捕捉那些未在 CoT 中明确
  描述的行为。要**读出字面之外的意思**；记住评测智能体未必知道正确答案与正确策略。
- 分析工具调用指标。大量冗余工具调用，可能说明分页参数或 token 上限**需要重新调参**；
  大量因无效参数导致的工具错误，可能说明工具需要**更清晰的描述或更好的示例**。

真实案例：我们上线 Claude 网页搜索工具时，发现 Claude 会**不必要地在查询参数后追加
「2025」**，导致搜索结果偏向、表现下降——我们通过改进工具描述把 Claude 引导回了
正确方向。

### 与智能体协作

你甚至可以让智能体分析你的结果并替你改进工具。把评测智能体的记录串接起来，粘贴进
Claude Code 即可。Claude 擅长分析记录并一次性重构大量工具——例如在新增改动后确保
工具实现与描述保持自洽。

事实上，**本文中的大部分建议都来自我们反复用 Claude Code 优化内部工具实现的过程**。
我们的评测搭建在内部工作区之上，映射了内部工作流的复杂度，包括真实项目、文档与
消息。我们依靠**留出测试集（held-out test set）**来确保没有对「训练用」评测过拟合。

留出测试集揭示了一个关键结论：即便工具已由我们的研究员手工写成达到「专家级」，
或由 Claude 自行生成，我们仍能从中**提取出额外的性能提升空间**。

## 编写高效工具的原则

### 为智能体选择正确的工具

**工具更多并不总是结果更好。** 我们观察到一个常见错误：工具只是把既有软件功能或
API 端点包一层——不管它是否真的适合智能体。原因在于：智能体与传统软件的
「可供性（affordance）」不同——它们感知自己能用这些工具做什么的方式不一样。

LLM 智能体的「上下文」是**有限的**（即一次能处理的信息量有上限），而计算机内存廉价
且充裕。设想在通讯录中查找某个联系人：传统程序可以高效地逐条存储和比对联系人。

但如果 LLM 智能体调用的工具**返回全部联系人**，然后不得不逐个 token 地读，这等于把
有限的上下文浪费在无关信息上（想象一下在通讯录里逐页从头读到尾来找人——就是暴力搜索）。
更好也更自然的做法（对智能体和人类 alike）是**先跳到相关的那一页**（也许按字母顺序定位）。

我们建议**构建少量精心设计、瞄准高影响工作流的工具**，与你的评测任务对齐，然后从
那里逐步扩展。在通讯录这个例子里，你可能会选择实现 `search_contacts` 或
`message_contact`，而不是 `list_contacts`。

工具也可以**整合功能**，在内部处理多个离散的操作（或 API 调用）。例如：

| 不推荐 | 推荐 |
|---|---|
| `list_users` + `list_events` + `create_event` | `schedule_event`（查询空闲时间并创建日程） |
| `read_logs` | `search_logs`（只返回相关日志行及少量上下文） |
| `get_customer_by_id` + `list_transactions` + `list_notes` | `get_customer_context`（一次性汇总客户近期且相关的信息） |

确保你构建的每个工具都有**清晰、区分明确的目的**。工具应当让智能体像人类在拥有
同样底层资源时那样，去细分并解决任务；同时减少那些原本会被中间输出消耗掉的上下文。

工具过多或功能重叠，也会让智能体偏离高效策略。**审慎、有选择地规划你要构建（或不
构建）哪些工具，回报非常可观。**

### 为工具做命名空间划分

你的 AI 智能体可能会接入数十个 MCP 服务器与数百个不同工具——包括其他开发者提供的。
当工具功能重叠或用途含糊时，智能体就会困惑于该用哪个。

**命名空间划分**（把相关工具归到共同前缀下）有助于在众多工具间界定边界；MCP 客户端
有时会默认这样做。例如**按服务划分**（`asana_search`、`jira_search`）或**按资源划分**
（`asana_projects_search`、`asana_users_search`），都能帮助智能体在恰当时机选中
恰当的工具。

我们发现，选择前缀式还是后缀式命名空间，对工具调用评测有**不可忽略的影响**；影响因
LLM 而异，我们建议你依据自己的评测来决定命名方案。

通过有选择地只实现那些**名字能反映任务自然细分**的工具，你同时降低了载入智能体上下文
的工具数量与描述长度，并把智能体式计算**从上下文卸载回工具调用本身**，从而降低整体
出错风险。

智能体可能调错工具、用错参数调用正确的工具、调用次数不足，或错误处理工具响应——
这些设计都能缓解上述问题。

### 从工具返回有意义的上下文

同理，工具实现应当**只向智能体返回高信噪比信息**。应优先保证上下文相关性而非灵活
性，并避免低层技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。像
`name`、`image_url`、`file_type` 这类字段，才更可能直接指导智能体的下游动作与响应。

**智能体对自然语言形式的名称、术语或标识符的处理能力，显著强于对晦涩标识符的处理。**
我们发现，仅仅把任意字母数字 UUID 解析为更具语义、更易解释的语言（甚至改为 0 起始的
ID 方案），就能通过减少幻觉**显著提升 Claude 在检索任务上的准确率**。

有时智能体需要同时接触自然语言与技术标识符（例如为了触发下游工具调用：
`search_user(name='jane')` → `send_message(id=12345)`）。你可以在工具中暴露一个简单的
`response_format` 枚举参数，让智能体控制返回「精简」还是「详尽」的响应：

```
enum ResponseFormat {
  DETAILED = "detailed",
  CONCISE = "concise"
}
```

实际效果示例：Slack 的 thread 与 thread 回复由唯一的 `thread_ts` 标识，获取 thread 回复
时必须提供它。`thread_ts` 及其他 ID（`channel_id`、`user_id`）可从「详尽」响应中获取，
以便发起需要这些 ID 的后续工具调用；「精简」响应只返回 thread 内容、不含 ID。在这个
例子里，使用「精简」响应大约只用了 **⅓ 的 token**。

即便是**响应的结构形式**——XML、JSON 还是 Markdown——也会影响评测表现，不存在一刀切的
方案。原因在于 LLM 是基于「预测下一个 token」训练的，**与其训练数据分布相近的格式
表现更好**。最优结构会随任务与智能体而变化，我们建议你依据自己的评测来选。

### 面向 token 效率优化工具响应

优化上下文的**质量**很重要，优化工具响应返回给智能体的上下文的**数量**同样重要。

对于任何可能占用大量上下文的工具响应，我们建议实现**分页、范围选择、过滤和/或截断**
的某种组合，并设置合理的默认参数值。对 Claude Code，我们默认将工具响应限制在
**25,000 token** 以内。我们预期智能体的有效上下文长度会随时间增长，但对**上下文高
效工具的需求会持续存在**。

如果选择截断响应，务必用有用的指令来引导智能体。你可以直接鼓励智能体采用更省 token
的策略——例如在知识检索任务中做**多次小而精准的搜索**，而不是一次宽泛的大范围搜索。
同样地，若工具调用抛出错误（例如输入校验阶段），你可以对**错误响应**做提示词工程，
清晰地传达具体、可执行的改进建议，而不是丢出晦涩的错误码或堆栈。

工具截断与错误响应能把智能体**引导到更省 token 的工具使用行为**（用上过滤或分页），
或示范正确格式的工具输入。

### 对工具描述做提示词工程

这是**提升工具效能最有效的方法之一**：对工具描述与规格做提示词工程。因为这些内容会被
载入智能体的上下文，它们能集体把智能体引导向有效的工具调用行为。

撰写工具描述与规格时，**想象你会如何向团队的新同事介绍这个工具**。把那些你可能
「默认对方知道」的东西——专用查询格式、小众术语定义、底层资源之间的关系——**显式
写出来**。通过清晰描述（并用严格的数据模型强制约束）预期的输入输出来消除歧义。
特别地，输入参数应无歧义命名：不要用 `user`，而要用 `user_id`。

有了评测，你能更有信心地度量这种提示词工程的影响。**对工具描述哪怕很小的改进，也可能
带来巨大的提升**：我们对工具描述做了精确改进后，Claude Sonnet 3.5 在 SWE-bench Verified
评测上达到了当时的最先进水平，错误率大幅下降、任务完成度显著提升。

更多工具定义最佳实践见 Developer Guide。如果你在为 Claude 构建工具，也建议了解工具是
如何被**动态载入** Claude 系统提示的。最后，如果你是在为 MCP 服务器编写工具，
**工具注解（tool annotations）**有助于披露哪些工具需要开放世界访问权限或会做出
破坏性更改。

## 展望

要为智能体构建高效工具，我们需要把软件开发实践**从可预测的确定性范式重新导向非确定性
范式**。

通过本文所述的、迭代式的评测驱动流程，我们识别出工具成功的稳定模式：**高效的工具
是刻意且清晰定义的，审慎地使用智能体上下文，能以多样方式组合进不同工作流，并让
智能体能直观地解决现实任务。**

我们预期，未来智能体与外界交互的具体机制会持续演进——从 MCP 协议的更新到底层 LLM
本身的升级。采用系统化、评测驱动的智能体工具改进方法，可以确保**随着智能体能力增强，
它们所依赖的工具也同步演进**。

**本节要点**

1. **工具是「确定性系统 ↔ 非确定性智能体」之间的契约**——设计思路必须随之改变，
   不能沿用给程序员写 API 的习惯。
2. **工具不是越多越好**：少而精、瞄准高影响工作流，并主动**整合功能**（`schedule_event`
   优于三个 list/create 工具）。
3. **上下文预算是稀缺资源**：默认分页/截断，Claude Code 上限 25,000 token；返回
   语义化字段而非 `uuid`。
4. **工具描述即提示词**：按「给新同事讲解」的标准写，参数名要无歧义——对描述的小幅
   精修能带来显著性能提升。
5. **评测是第一性的**：没有评测就无法度量改进，`--teleport` 式的能力提升都无从谈起。

**与课程关联**：本文与 `how-long-contexts-fail`、`context-rot` 构成「上下文工程」主线——
前者讲如何**供给**高质量上下文，后两者讲上下文过长时**为什么失败**。
