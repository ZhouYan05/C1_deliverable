# 长上下文为何会失效

### 管好你的上下文，是智能体成功的关键

随着前沿模型的上下文窗口不断增大¹，其中许多已支持高达 100 万 Token，我看到许多兴奋的讨论，认为长上下文窗口将解锁我们梦想中的智能体。毕竟，只要窗口足够大，你就可以把可能需要的一切——工具、文档、指令等等——统统塞进提示词里，剩下的交给模型处理即可。

长上下文让检索增强生成（RAG）的热情受挫（既然能把所有文档都塞进提示词，何必再去找到最佳的那一篇！），催生了模型上下文协议（MCP）的热潮（连上所有工具，模型就能胜任任何工作！），也点燃了人们对智能体的热情²。

但事实上，更长的上下文并不会带来更好的回答。上下文过载会让你的智能体和应用以出人意料的方式失败。上下文可能被污染、变得分散注意力、令人混淆或相互冲突。这对智能体来说尤其成问题，因为智能体依赖上下文来收集信息、综合结论并协调行动。

让我们先梳理上下文失控的各种方式，再回顾缓解或彻底避免上下文失效的方法。

## 上下文失效

- 上下文污染（Context Poisoning）：当幻觉进入上下文时
- 上下文干扰（Context Distraction）：当上下文压过训练所学时
- 上下文混淆（Context Confusion）：当多余内容影响回答时
- 上下文冲突（Context Clash）：当上下文的各部分相互矛盾时

---

### 上下文污染

上下文污染是指幻觉或其他错误进入上下文，并在其中被反复引用。

DeepMind 团队在 Gemini 2.5 技术报告中指出了上下文污染问题，我们上周也对此做过解读。在玩宝可梦时，Gemini 智能体会在游戏过程中偶尔产生幻觉，从而污染自己的上下文：

> 这一问题的一种尤其恶劣的表现形式就是"上下文污染"——上下文的许多部分（目标、摘要）被关于游戏状态的错误信息"污染"，而这往往需要很长时间才能消除。结果是，模型会执着于达成不可能实现或毫不相关的目标。

如果其上下文中的"目标"部分被污染，智能体就会制定出荒谬的策略，并为了一个无法达成的目标反复做出某些行为。

### 上下文干扰

上下文干扰是指上下文变得过长，导致模型过度聚焦于上下文，而忽视了训练期间学到的东西。

在智能体式工作流中，随着模型收集更多信息、积累更多历史记录，上下文不断增长——这些积累的上下文非但不能提供帮助，反而会形成干扰。玩宝可梦的 Gemini 智能体清楚地展示了这个问题：

> 虽然 Gemini 2.5 Pro 支持超过 100 万 Token 的上下文，但要让智能体有效利用它，仍是一个全新的研究前沿。在这一智能体式设置中，人们观察到，当上下文显著增长超过 10 万 Token 时，智能体表现出一种倾向：更愿意重复其庞杂历史中的既有动作，而不是综合出新的计划。这一现象虽然只是个案，却凸显了一个重要区别：用于检索的长上下文与用于多步生成式推理的长上下文是两回事。

智能体没有利用训练所学来制定新策略，而是执着于从庞大的上下文历史中重复过去的动作。

对较小的模型来说，干扰的上限要低得多。Databricks 的一项研究发现，Llama 3.1 405b 的正确率在约 3.2 万 Token 处开始下降，而更小的模型下降得更早。

如果模型远在上下文窗口填满之前就开始失常，那超大上下文窗口的意义何在？简而言之：摘要生成³和事实检索。如果你做的不是这两件事，就要当心所选模型的干扰上限。

### 上下文混淆

上下文混淆是指模型利用上下文中的多余内容，生成了低质量的回答。

有那么一阵子，似乎人人都打算发布一个 MCP 服务器。一个强大的模型连接着你所有的服务与各类应用，替你完成所有琐碎任务——这个梦想似乎触手可及。只要把所有工具描述扔进提示词，点击运行即可。Claude 的系统提示词给我们指了路，因为它主要由工具定义或工具使用说明组成。

但即便整合与竞争没能让 MCP 降温，上下文混淆也会。事实证明，工具确实可能太多。

伯克利函数调用排行榜（Berkeley Function-Calling Leaderboard）是一个工具使用基准测试，用于评估模型有效利用工具来回应提示词的能力。该排行榜现已推出第三版，结果显示：当提供不止一个工具时，每个模型的表现都会变差⁴。此外，伯克利团队"设计了所有提供的函数都不相关的场景——我们期望模型不进行任何函数调用"。然而，所有模型都会偶尔调用不相关的工具。

浏览函数调用排行榜就能看到，模型越小，问题越严重：

最近一篇论文给出了上下文混淆的一个鲜明例子：该论文在 GeoEngine 基准上评估小模型的表现，该测试包含 46 种不同的工具。当团队给量化（压缩）版 Llama 3.1 8b 一个包含全部 46 种工具的查询时，它失败了——尽管上下文远未超出 1.6 万 Token 的上下文窗口。而当只提供 19 种工具时，它成功了。

问题在于：只要把东西放进上下文，模型就必须关注它。它可能是不相关的信息或多余的工具定义，但模型都会将其纳入考量。大模型——尤其是推理模型——越来越擅长忽略或丢弃多余的上下文，但我们仍不断看到无用的信息让智能体栽跟头。更长的上下文让我们能塞入更多信息，但这种能力也有代价。

### 上下文冲突

上下文冲突是指你在上下文中累积的新信息和工具，与上下文中的其他信息相冲突。

这是比上下文混淆更棘手的问题：这里的坏上下文并非无关，而是与提示词中的其他信息直接矛盾。

微软与 Salesforce 的一个团队在最近一篇论文中出色地记录了这一点。该团队从多个基准测试中取来提示词，并将其中信息"分片"到多个提示词中。可以这样理解：有时你会坐下来，把一段段文字输入 ChatGPT 或 Claude 之后再按回车，把每个必要的细节都考虑周全；另一些时候，你可能先从一个简单的提示词开始，等聊天机器人的回答不尽如人意时，再补充更多细节。微软/Salesforce 团队把基准提示词改造成类似这种多步交流的形式：

左侧提示词中的所有信息都包含在右侧的几条消息中，而这些消息会在多轮对话中逐一展开。

分片后的提示词带来了显著更差的结果，平均得分下降了 39%。该团队测试了一系列模型——OpenAI 引以为傲的 o3，得分从 98.1 跌到了 64.1。

这是怎么回事？为什么信息分阶段收集（而非一次性全部给出）会让模型表现更差？

答案是上下文混淆：拼装起来的上下文包含完整的聊天记录，其中保留着模型在掌握全部信息之前就尝试作答的早期内容。这些错误答案一直留在上下文中，并在模型生成最终答案时影响它。该团队写道：

> 我们发现，大语言模型（LLM）常常在早期轮次中做出假设，过早地尝试生成最终解决方案，并对其过度依赖。简单来说，我们发现当 LLM 在对话中走错一步，就会迷失方向，无法恢复。

这对智能体开发者来说可不是好兆头。智能体从文档、工具调用以及负责子任务的其他模型那里拼装上下文。这些来自不同来源的上下文，都有可能自相矛盾。此外，当你连接并非自己创建的 MCP 工具时，它们的描述和指令与提示词其余部分发生冲突的可能性就更大。

---

百万级 Token 上下文窗口的到来，曾让人感觉具有变革意义。把智能体可能需要的一切都塞进提示词的能力，激发了人们对超级智能助手的想象：它能够访问任何文档、连接所有工具，并保持完美的记忆。

但正如我们所看到的，更大的上下文催生了新的失效模式。上下文污染埋下的错误会随时间不断累积。上下文干扰让智能体过度依赖上下文，重复过去的动作而非向前推进。上下文混淆导致无关工具或文档被误用。上下文冲突制造内部矛盾，使推理脱轨。

这些失效对智能体的打击最为沉重，因为智能体恰恰运行在上下文膨胀的场景之中：从多个来源收集信息、连续进行工具调用、开展多轮推理、积累冗长的历史记录。

幸运的是，解决办法是有的！在接下来的一篇文章中，我们将介绍缓解或避免这些问题的技术，从动态加载工具的方法，到建立上下文隔离区。
