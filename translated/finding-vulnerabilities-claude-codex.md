# 使用 Claude Code 和 OpenAI Codex 挖掘现代 Web 应用漏洞 | Semgrep

TL;DR：我们评估了 AI 编码智能体在真实代码中查找漏洞的有效性。

- 方法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且规模较大的开源 Python Web 应用中查找漏洞。它们共产生了 400 多个安全发现，由我们的安全研究团队逐一审核。
- AI 编码智能体能找到真实漏洞：Claude Code 找到 46 个漏洞（真阳性率（TPR）14%，误报率（FPR）86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个是高危漏洞。
- AI 能把握上下文，却在数据流上受阻：Claude Code 最擅长发现不安全的直接对象引用（IDOR）漏洞，真阳性率（TPR）达 22%（报告 59 个，正确 13 个），但在跨多个文件和函数进行污点跟踪方面表现吃力，SQL 注入的 TPR 仅为 5%（2/38），XSS 为 16%（12/74）。OpenAI Codex 未能报告任何正确的 IDOR（TPR 0%，0/5），SQL 注入（0%，0/5）和 XSS（0%，0/28）表现也很差，但出人意料的是，它报告的路径遍历正确数量超过了 Claude Code，TPR 达 47%（8/17）。
- 非确定性是真实存在的难题：在完全相同的代码库上多次运行完全相同的提示词，结果往往大相径庭。在其中一个应用中，三次完全相同的运行分别产生了 3 个、6 个和 11 个不同的发现。

关键要点：

- 配备相对简单的安全导向提示词的 AI 编码智能体，已经能够在真实应用中找到真实漏洞。
- 但是：根据漏洞类别的不同，结果可能会相当嘈杂（误报率高），尤其是在 SQL 注入、XSS 和服务端请求伪造（SSRF）等传统注入类漏洞上。
- 详细的评估和基准测试是理解某种方法在查找漏洞方面有效程度的关键（这一点一直如此，而面对 LLM 这类非确定性工具时更是如此），也能让你知道自己的改进方向是否正确。

## 引言

在 Semgrep，应用安全（AppSec）就是我们的全部。长期以来，我们一直在产品中落地 AI（Assistant 背后的技术、用于测试 AI 工作流的 promptfoo、利用安全研究员的分诊来评估自动分诊的性能），不断研究传统确定性分析与现代 AI 上下文能力的组合方式，而不去追逐潮流。

这项研究正是这一持续使命的一部分。我们正在开启一次深入的公开探索，以回答一个萦绕在每个人心头的问题：大语言模型（LLM）在源代码中查找漏洞的实际效果究竟如何？

## 关于基于 AI 的漏洞挖掘的开放性研究问题

为了指导我们的研究，我们将「LLM 擅长找 bug 吗？」这一宽泛问题拆解成了更具体、可衡量的子问题。

- 基于 LLM 的漏洞查找的误报率和漏报率分别是多少？是否会因编程语言、框架、代码库规模或漏洞类别而异？对代码的写法又有怎样的敏感性？
- 造成误报和漏报的常见原因有哪些？
- 分析的确定性如何？每次都能得到相同的结果吗？

针对注入类漏洞，我们特别想了解：

- LLM 在源（source，如用户提供的值）和汇（sink，如执行原始 SQL 查询的方法）之间跟踪用户输入的效果如何？
- 它能否跨函数、跨文件跟踪数据？
- 它能否对净化函数及其他安全控制进行推理？
- 它能否对来自第三方开源依赖的函数进行推理？

## 常见 SAST 基准测试的问题：缺乏真实感

在深入讨论我们的发现之前，先来谈谈我们如何衡量 AI 的性能。当前大量的研究/论断都依赖基准测试，这些基准测试虽然有价值，却无法完全反映真实世界代码的复杂性。

- 带有已知漏洞的应用：这类基准测试只使用带有已知漏洞的开源应用；多亏 Kinnaird McQuade 整理的 vulnerable-apps，其中许多应用都能找到。如果你读过本博客，可能会认出 WebGoat、JuiceShop、OWASP Benchmark 等名字。但这类基准测试存在一个问题：当前 LLM 很可能已经「消化」过这些仓库的代码以及互联网上的大量公开分析文章，从而拥有了先验知识，使结果产生偏差。这些应用的代码往往并不真实，充斥着大量注释、注解和变量名，它们或暗示或直接指明了漏洞所在的位置以及利用方法。有时，连工具的结果都被提交进了仓库（javaspringvulny 的 SearchService.java 来自 juiceshop，挑战就写在文件名里？）。
- XBOW 为自动化渗透测试工具提供了基准测试，但并不适合静态分析：代码往往过于刻意和简化，无法代表真实应用。ZeroPath 对它们进行净化处理后效果不错，但只有一小部分经过了净化。此外，这些测试用例中的每一个都是微型应用，专门为触发特定的攻击场景而设计。以 Python 基准测试为例，XBOW 有 45 个这样的用例：45 个不同的微型应用，平均不到 98 行代码、3 个 Python 文件。这个规模太小，无法体现跨整个代码库或多个函数进行搜索和推理的复杂性。
- CVE 记忆偏差：LLM 是在互联网上的海量公开数据上训练的，其中就包括发现并修复 CVE 的那些代码库本身。这造成了根本性的数据污染问题。AI 可能并不是通过新颖的分析检测出漏洞，而只是识别出了它在训练时记住的模式。

最近，学术界设计了 CyberGym、Eyeballvul、SecVulEval 等基准测试。它们有了很大改进，更接近真实世界的示例，但仍缺乏对现代 Web 应用的关注，或者将漏洞从更广泛的应用上下文中剥离了出来。

- EyeballVul：由 Timothée Chauvin 推出的较新基准测试，它从开源项目中提取经人工审核的真实漏洞，并将其呈现为最小化、可复现的测试用例。虽然基于真实代码，但它仍然将漏洞从更广泛的应用上下文中孤立出来，使搜索问题变得更容易。
- SecVulEval 和 CyberGym：这些套件旨在评估 C 或 C++ 中的漏洞。虽然它们在各自领域很有价值，但对 C 和 C++ 的关注意味着这些数据不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

虽然每种方法都各有用途，有时也应当使用，但它们未必反映现代软件开发的现实。真实世界的应用并不是干净、孤立的函数，而是由依赖、框架和业务逻辑交织而成的复杂网络。

我们的方法有所不同。我们在 11 个基于 Python、积极维护的大型开源项目上进行了测试，这些项目使用常见 Web 框架（Django、Flask、FastAPI）编写。我们的方法是对前述方法的补充，我们相信它的独特之处在于：a）旨在代表真实世界中 AI 驱动的漏洞查找（而非小型、孤立的合成示例）；b）不受模型训练数据的污染；c）代表了大多数开发者和公司实际构建的应用类型——使用现代语言和框架的 Web 应用。

我们对 11 个应用进行了分析，然后人工分诊了全部 445 个发现，并对其中大部分（尤其是 IDOR 或认证绕过）进行了动态验证。

### 我们的发现

- 今天的 Claude Code 和 Codex 都已经很有用：它们能发现真实的安全漏洞，但噪音非常大。整体噪音仍然很高，但它们确实在这些流行的开源 Python Web 应用中发现了真实的安全漏洞。总体而言，Claude Code 找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。
- 许多 IDOR 漏洞乍看之下判断正确，且 Claude Code 提出了可信的修复方案：LLM 不仅能发现这些漏洞，还能给出可信的修复建议，例如依据代码中已有的模式注入新的权限检查。IDOR 问题很难分诊，我们不得不对其中大多数进行实际测试才能确认，这使得真阳性率大幅降低。
- Claude Code 是一个好的安全护栏工具吗？许多发现虽然在技术上属于误报，但仍然是合理的「护栏」建议，或者看上去很像。例如，模型常常建议对一条本来就已经安全的 SQL 查询进行参数化。虽然算不上漏洞，但这能增强代码的健壮性。我们仍将这些视为误报，只不过没有其他误报那么严重。然而，这些代码加固建议并非总能信任。我们发现若干实例（尤其是客户端 JavaScript 代码中），AI 试图修复它认为存在的 DOM 操作问题，但实际上却破坏了代码（在我们观察到的案例中，对 HTML 进行了双重转义），而那里一开始就根本不存在安全问题。
- XSS 和 SQL 注入——难以将各组件拼凑起来：模型难以追踪数据从服务端框架流向客户端组件（XSS 的常见模式）或流经复杂应用层的过程。它常常被静态定义的数据搞糊涂，或者无法识别服务端的净化处理。
- 重复提示词有助于获得更多结果：LLM 的概率特性意味着，以略微不同的方式提出同一问题就能产生新的发现，这凸显了分析的不一致性。在同一代码库上多次重复同一提示词会得到不同的答案，但最终还是会绕回相同的发现。
- OpenAI Codex 有时无法输出有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们考虑了这些文件中报告的所有发现，但它们并不是有效的 SARIF 或 JSON。在我们测试的所有场景中，Claude Code 都不存在这个问题。

## 同样的代码、同样的 AI，每次找出的漏洞却不同：AI 编码智能体的非确定性问题

为了探索非确定性在实际中的表现，我们从中选取了三个应用，针对同一个安全问题——IDOR——用同一提示词运行了多次。一个规律浮现出来：每次运行测试，AI 的发现都各不相同。

在漏洞检测的语境下，这是一个重大问题。首先，作为安全工程师，我们理想中希望对重要漏洞类别的扫描有比「希望模型这次搜索得足够彻底」更强的保证。

其次，间歇性地检测出漏洞会给安全工具或漏洞管理系统带来不一致和噪音。例如，如果你在使用 SAST 平台、ASPM 或内部自研的工具，这些系统往往假定：之前检测到的漏洞不再出现，就意味着它已被修复。但在 LLM 驱动的检测中情况未必如此，因为单次扫描可能会漏掉它，于是后续扫描再次发现同一问题时就会创建一个「新」发现，导致重复的 JIRA 工单和开发人员的困扰。

以下是我们观察到的一些具体例子：

- PY-APP-007：在第一次运行中，AI 识别出一个「缺少搜索授权」的漏洞，而另外两次运行都没有发现它。第二次运行标记出了该次运行独有的问题。第三次运行则找到了属于自己的一套不同漏洞。
- PY-APP-006：情况类似：第一次运行在用户 API 中发现了一个漏洞，而后续运行则聚焦于代码库的其他部分，如活动摘要和笔记模块。
- PY-APP-002：这里的变异性或许最为明显。识别出的漏洞数量从第一次运行的 3 个跃升至第二次的 6 个，再到 11 个。每次运行给出的发现都不同，且只有部分重叠。

那么，这背后的原因是什么？我们认为关键因素就是所谓的上下文劣化和压缩。当 AI 智能体被要求分析整个代码库时，它要处理海量信息：上下文劣化会导致它无法从自己的上下文中准确检索信息。为了应对这一点，LLM 使用了一种有损压缩（有时称为压缩），这意味着一些更精细的推理细节，如函数名、路径等，可能在摘要过程中丢失。

可以把它想象成试图概括一部冗长而复杂的小说：你能抓住主要情节，但必然会遗漏一些细微之处和微妙差别。同样地，AI 可能会忘记某个特定的架构模式或某条微妙的数据流，导致它在某次运行中漏掉一个漏洞，而在另一次运行中又能发现它。我们在 PY-APP-006 中看到了一个明显的例子：AI 提出的某个修复方案并不完整，因为它未能复用现有的用户授权基类——这是一段关键的上下文，似乎在那次运行中丢失了。

这种非确定性对我们构建 AI 原生 SAST 的方式有着深远影响。一方面，AI 每次以不同方式「思考」的能力意味着它可以探索更广泛的潜在攻击向量，就像一支视角多元的人类渗透测试团队。另一方面，它也引入了一定程度的不确定性，可能导致混乱或行为失常。

- 覆盖不完整：单次运行可能带来虚假的安全感，因为它可能漏掉本会在后续运行中被发现的关键漏洞。
- 缺乏可复现性：无法复现结果，使得我们难以验证 AI 的发现，也难以以一致、可重复的方式信任其输出。
- 成本与时间增加：为了获得更完整的图景而需要多次运行审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦编写完成，再次运行基本「免费」（不计硬件成本、电费等）。但重度依赖 LLM 的工具并非如此，在这种情况下，读取代码库并对其进行推理，每次扫描可能要花费数十到数百美元的令牌（Token）成本。对于今天的模型，这一成本可能会随时间下降，但更新的模型可能更昂贵。

## Claude Code 新推出的 /security-review 命令效果如何？

Anthropic 为 Claude Code 发布了一个名为 /security-review 的新命令。它的设计用途是在拉取请求（PR）上运行，检查变更的文件并提出问题，以识别特定的安全问题。你可以在这里找到该提示词。

当在整个代码库上运行该命令时，我们发现它识别出的安全问题相当有限。很多时候，它无法找到我们让 Claude Code 一次只搜索某一类特定安全问题时所能得到的那些问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了该命令，结果它在这三个应用上总共只发现了一个 XSS，这与我们在整体实验中取得的结果大相径庭。

## 回答我们的问题

让我们根据所学到的经验，重新审视最初的研究问题。

- 误报率/漏报率是多少？对于直接应用于真实世界代码的原始 AI，误报率非常高：最好时 Codex 的路径遍历为 53%，Claude Code 的 IDOR 为 78%；最差时 Claude Code 的 SQL 注入达 95%，Codex 的 SQL 注入和 IDOR 达 100%。性能在不同应用之间差异也很大：PY-APP-002（Claude Code）的真实 IDOR 达到 100%（10/10），而 PY-APP-007 为 0%（0/7）。综合所有应用和所有报告的问题，Claude Code 找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。由于我们使用的是真实应用，本实验无法精确衡量漏报。我们将在后续博客文章中介绍衡量漏报率的技术！
- 为什么会失败？我们观察到的主要弱点是：对于注入类问题，模型缺乏对代码执行的深层语义理解。模型在跨过程污点流和隐式流上表现吃力，而这正是传统 SAST 引擎的看家本领。部分局限也来自上下文压缩和上下文劣化。我们将继续更详细地探索这些局限，并寻找缓解方案。
- 脚手架和智能体式工作流有多重要？它们不仅重要，而且正变得不可或缺。AI 在安全审查领域的未来不是单一的整体模型，而是一个 AI 智能体系统（包括我们案例中这样的编码智能体），它们能够使用工具、对证据进行推理，并相互协作以发现和验证漏洞。虽然我们（目前）还没有关于「使用可访问 Claude Code 的智能体」与「对推理模型采用更典型的上下文工程（即搭建脚手架以提供所有相关代码）」之间差异的数据，但我们观察到，系统在完成复杂流程并在报告安全问题的过程中做出明智决策的能力存在巨大差异。话虽如此，Sean Heelan 是一个反例——他通过充分的上下文工程，让推理模型报告出了一个漏洞（成功率为 8%）。我们强烈建议你阅读他的博客文章。
- 这一切的成本如何？遗憾的是，我们未能统一跟踪 Claude Code 和 Codex 之间的成本。对于所有这些漏洞和所有这些应用，Claude Code 的总成本为 114 美元（不包括非确定性测试和 /security-review 命令的运行）。

## 数据集：未来发布

我们今天既不会发布数据集，也不会公布所分析开源应用的名称，因为我们正处于负责任披露的流程中，正在联系应用开发者修复并验证所有安全问题。待流程完成，我们就会放心地发布数据。

## 结论

大语言模型（LLM）并不是明天就能取代人类安全工程师的银弹，事实上，它们在端到端发现高危注入类漏洞方面还相当薄弱。然而，它们也是极其强大的工具。我们的研究表明，理解它们的优势（上下文推理）和劣势（代码的深层语义），并围绕它们构建以先进静态分析引擎为支撑的复杂智能体式系统，我们就能创造出远比以往任何工具都强大的新一代安全工具。
