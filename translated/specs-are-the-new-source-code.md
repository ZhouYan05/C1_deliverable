# 规格说明已死，规格说明万岁！

### 原型是新的规格说明，而规格说明是新的……源代码？

Ravi Mehta
和
Danny Martinez
2025 年 7 月 31 日

回顾我的职业生涯，规格说明（Spec）变得越来越短。我刚入职微软时，一名 PM（产品经理）的价值是以其规格说明的分量来衡量的。多年后，在 Tripadvisor，我们把那位带着一份草草写在餐巾纸上的规格说明来参加产品评审的 PM 奉为传奇。

产品团队常常把规格说明当作文书工作——在交付这一「真正的工作」之前不得不应付的苦差事。工程师因优雅的代码而受到赞誉，设计师因出色的用户体验（UX）而受到认可，PM 则因交付影响力而获得嘉奖。但规格说明呢？它们通常被匆匆赶完、随手丢开，然后被遗忘。

感谢阅读《Ravi on Product》！免费订阅即可接收新文章，并支持我的创作。

这一直是个错误。在我的产品能力工具箱（Product Competency Toolkit）中，功能规格说明（Feature Specification）高居榜首——十二项能力中的第一项——自有其道理。它与产品交付（Product Delivery）、产品质量（Product Quality）一起，支撑着产品执行（Product Execution）。

无懈可击的执行是优秀产品管理的基石，而一份出色的规格说明是这一切的起跑线。

如今，我们的构建方式正在发生转变。工程师的速度越来越快——快得多。AI 能在几分钟内把粗略的想法变成可运行的代码。瓶颈不再是「构建」，而是「知道该构建什么」，并让团队围绕这些需求达成一致。

忽然之间，朴素的规格说明不再是转瞬即逝的文书工作。它是产品管理的基石——它正在成为源代码本身。

## 为什么 PM 突然成了瓶颈

在最近的演讲《用 AI 更快地构建》（Building Faster with AI）中，Andrew Ng 指出了一个前所未有的趋势：

> 「我有生以来第一次看到有管理者向我提议，让 PM 的数量达到工程师的两倍。我至今不确定这个提议是否是个好主意，但我认为这预示着世界的走向。」——Andrew Ng

这印证了我们在上一篇文章中的预测：随着工程师在 AI 的帮助下交付速度快上数倍，公司需要更多而非更少的 PM 来支撑这些高产的工程师。

随着产品交付不断加速，产品管理的其他所有环节都承受着巨大压力——理解客户需求、打造合适的功能、验证实际影响。

而所有这些压力最终都汇聚到一件产物上——规格说明。

## 规格说明——新的源代码

在传统软件开发中，程序员编写人类可读的「源代码」，它被编译成高度优化、机器可读的「目标代码」。「目标代码」（也叫二进制文件）是一种副产品，可以借助源代码重新生成。源代码才名副其实地是事实之源。

来自 OpenAI 的 Sean Grove 提出了一个颇具挑衅性的论点。在最近的演讲《新的代码》（The New Code）中，他主张，精心编写的提示词（也就是规格说明）才是新的源代码。

从这个角度看，我们做 AI 开发的方式完全反了。我们精心撰写提示词，向模型传达我们的意图；AI 生成代码；然后我们保留代码，却把提示词扔掉。

「这感觉就像是把源代码撕碎，然后煞费苦心地对二进制文件做版本管理。」Grove 评论道。

想一想吧。在传统编程中，源代码是神圣的。源代码包含注释、结构和文档——理解并修改系统所需的一切。二进制文件只是下游的产物。

但有了 AI 之后，我们把这种关系颠倒了过来。我们把生成的代码当作值得保留的产物，而把规格说明——提示词——当作一次性用品。

Grove 认为这完全弄反了。代码——即便是优雅的代码——用他的话说，只是规格说明的一种「有损投影」。正如反编译二进制文件无法还原最初的注释和变量名，阅读代码也无法告诉你它背后的完整意图。

而规格说明则包含了一切。一份足够扎实的规格说明可以生成「优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客」。

> 一份足够扎实的规格说明可以生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。——Sean Grove，OpenAI

更重要的是，规格说明能做到代码做不到的事：让人类和机器围绕共同目标对齐。Grove 说得直白：「一份书面规格说明能有效地对齐人类，它是你用来沟通、讨论、辩论、参照和同步的产物。」

他预测：「在不远的将来，最擅长沟通的人就是最有价值的程序员。毫不夸张地说，只要你能有效沟通，你就能编程。」

新的稀缺技能不再是编码，而是撰写能够完整捕捉意图与价值的规格说明。

对产品经理来说，这应该很耳熟。这正是我们一直在做的事——只不过现在，机器也在倾听。

## 等等，原型不是早就把规格说明干掉了吗？

直到不久之前，产品生命周期都必须从规格说明开始——无论是产品需求文档（PRD）、概念文档还是餐巾纸——由此启动最初的线框图绘制、设计、原型制作和 MVP（最小可行产品）开发。

传统做法给人的感觉像是一种必要的苦差事。工程师们构建最基础的 MVP，只为把某个东西——任何东西——送到客户手中。「如果你没有为产品的第一版感到难堪，那说明你发布得太晚了」成了金科玉律。

我们构建产品的整套方法最近经历了一次重大转变，在这个新世界里，规格说明往往是产出，而非输入。

如今，你无需发布一行代码，就能把原型送到客户手中。v0、Lovable、Replit 之类的工具让你在几小时而非几周内构建出可用的原型，完全不需要工程能力。

这不只是更快——而是根本性的不同。凭借 Vibe Coding 做出的原型，你可以在动手写功能规格说明之前，就先收集到真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

- 旧的工作流是这样的：模糊的想法 → 线框图 → 设计稿 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格说明修订 → 线框图 → 设计稿 → 重建 → 祈祷。
- 新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰透彻的规格说明 → AI 辅助实现。

原型并没有干掉规格说明，反而让规格说明变得更好。

## 规格驱动开发实战

让我们看一个实操案例，了解这一切是如何展开的。Danny Martinez 是 decimals 的创始人，这是一个（尚处隐身模式的）平台，帮助创作者经济领域的专家把其网络中的人才安排到工作岗位。

---

- 你是一位 AI 优先的 PM、正在寻找新的机会吗？留下你的信息，当我们遇到有趣的职位机会时会通知你。
- 你是正在招聘 AI 优先 PM 的公司吗？申请加入我们的人才网络，我们会分享一份精心筛选的候选人短名单。

---

Danny 将带我们走一遍他们的规格驱动开发流程——这一流程带来了两方面的影响：

- 对于较大的功能，极大改善了与工程团队的沟通；
- 让没有任何编程经验的 Danny，也能从详细规格说明一路走到上线功能，独立搞定较小的需求。

下面交给 Danny——

这是我最近处理的一个例子。先交代背景：我们正在构建一款产品，帮助资深网红把其网络中的候选人推荐到工作岗位。新落地页上线后，我们需要给这些专家提供一个快速访问自己页面链接的途径。

> 我们需要在页头加一个按钮，指向公司申请页。我目前正忙着处理邮件。如果你能接手的话，这个用 Vibe Coding 就能搞定。

这是我联合创始人发来的，指的是一个需要上线的简单按钮。足够简单，也恰恰是非技术人员如今可以自己交付的那类事情。

下面是这套配置以及它如何在几分钟内完成交付的步骤：

- 项目管理工具：Linear
- IDE：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP（模型上下文协议）服务器：Linear MCP 服务器，让 Copilot 能够访问 Linear 工单

让我们看看流程中的各个步骤（可对照上方的 Loom 视频同步操作）：

- 根据我联合创始人的 Slack 消息生成一个 Linear 工单（00:14）
- 在上述工单中明确我想要的新文案（00:25）
- 打开 Copilot，提示 Claude 打开该 Linear 工单（01:18）
- 提示 Claude 审阅该工单，并结合代码库进行分析（01:52）
- 提示 Claude 创建分支并实现这些改动（02:30）
- 测试这些改动，确认其按预期工作。（02:52）
- 在 GitHub 上发起拉取请求（PR），把这些改动合入代码库（03:55）
- 等待工程师审阅/批准该 PR

把镜头拉远，这套配置的真正威力便显现出来。是的，这只是个微不足道的例子，但要点不变：一个非技术人员现在只需通过 GitHub Copilot 向 Claude 发送几句提示词，就能在 Linear 工单、代码库和工程师之间自如穿行。

再说一遍，这一切中最关键的部分不是代码本身，而是规格说明。

不过，需要提醒的是，要让上述流程顺畅运作，还需具备以下条件：

- 具体明确：含糊的规格说明只会换来一团糟的代码库。让 Claude 先拿到工单初稿、审阅代码库，并帮助把需求写得更具体，是流程中不可或缺的一环。就我们而言，我们还制定了撰写优质规格说明的指南。
- 有所取舍：上述流程最适合用于简单任务。工单越复杂，就越需要懂行的人介入（在这些情况下，「自助」最终一点也不自助）。
- 严格把关：这套方法之所以行之有效，是因为有一位真正懂行的工程师在审阅改动，确保简单性与功能性之间的平衡得以维持。

但我们要说清楚：规则已经变了。规格说明是所有产品构建者的事实之源，包括大语言模型（LLM）在内。

有了恰当的配置，以非技术人员的身份为代码库做贡献是完全现实的。只要有足够的时间和耐心，你就能开始理解代码库并亲自实现改动，而不是每次都靠 Claude 来救场。

有朝一日，你甚至可以期待一个 AI 智能体在你悠闲品咖啡时把你的工单交付上线。

如果你是一名 PM，正在担心 AI 会对你的工作做什么，关键是要意识到：这份工作本身正在改变。不过其他人也都一样。好消息是，成为一名优秀 PM 所需的核心技能，在这个新世界里变得更加珍贵。

正如我们在上一篇文章中所预测的，以这种方式运作的公司将需要更多而非更少的 PM。事实证明，这一预测应验得相当不错：

## 规格说明万岁！

科幻作家 William Gibson——「赛博空间」一词的创造者——曾说过：

> 未来已经到来——只是分布得还很不均匀。

每当我思考 AI 能做什么、不能做什么时，就会想起这句话。如今，AI 的进展极不均衡。有些事——生成代码、文本、图像——已经实现了质的飞跃，以 AI 的速度运转。另一些事——与客户交谈、发现他们的需求、说服他们购买——仍以人类的速度推进。

这种不均衡的分布正在重塑产品团队。聚光灯正从实现工作转向理解工作。那些一直让顶尖 PM 脱颖而出的核心技能——理解用户需求、清晰定义问题、设计优雅的解决方案——如今的价值已呈指数级增长。

最优秀的 PM 会把这些洞察转化为规格说明——它们能让团队对齐、指导实现，并在这个日益自动化的开发世界中成为经久不衰的产物。
