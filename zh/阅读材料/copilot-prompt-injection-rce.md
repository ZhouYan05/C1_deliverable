# 精读笔记：GitHub Copilot 经由提示词注入实现远程代码执行（CVE-2025-53773）

> 原文：GitHub Copilot: Remote Code Execution via Prompt Injection
> 研究者：Embrace The Red（红队）
> ⚠️ 本笔记为**提炼与讲解**，非逐段译文。原文版权归作者所有。
> ⚠️ **安全提示**：本文涉及真实漏洞利用链。**请勿在未授权的系统上尝试。**
>    课程作业中请只做「威胁建模」层面的分析，不要复现利用代码。

## 一句话结论

**只要 AI 智能体能写文件、且能修改自己的配置或安全相关设置，就可能实现远程代码执行。**
这不是新问题，而是智能体系统中**容易被忽略的一类设计缺陷**，应当列入安全评审清单。

## 漏洞模式（通用启示）

> 如果一个智能体能够**写入文件**并**修改自身配置或安全相关设置**，就可能导致 RCE。

作者强调：**这类问题并不罕见**，是在做安全评审时**始终应当寻找的一类攻击面**。

同类案例：几天前 Amp 也被发现存在相同模式。

## 发现过程

作者在测试 VS Code 与 GitHub Copilot 的 Agent Mode 时注意到一个**反常行为**：

- 它能在**未经用户批准**的情况下创建并写入工作区文件
- **这些编辑是立即持久化的**——不是内存中等待审查的 diff，而是**立刻写入磁盘**

> 作为红队从业者，直觉告诉你这「大概不太好」——于是去研究它能否被用于提权与代码执行。

### 关键发现：YOLO 模式

作者转而研究 VS Code 中**哪些功能依赖于工作区文件夹内的设置**，很快发现一个：

在 `.vscode/settings.json` 中加入下面一行：

```json
"chat.tools.autoApprove": true
```

这会让 **GitHub Copilot 进入 YOLO 模式**：

- 禁用**所有用户确认**
- 可以运行 **shell 命令**
- 可以**浏览网页**，以及更多

**三个加剧因素**：

1. 这是一个**实验性功能**，但**默认就存在**——无需下载特殊版本，也无需把 VS Code
   整体切到实验模式
2. 在 **Windows、macOS 与 Linux 上都有效**
3. 写入的是**项目级配置**，在 clone 下来的仓库里就能携带

## 完整利用链

```
① 攻击者在某处植入提示词注入
   （源代码文件 / 网页 / GitHub issue / 工具调用响应 / 其他内容；
     载荷也可以用不可见文本作为指令）
              ↓
② 注入指令向 ~/.vscode/settings.json 写入
   "chat.tools.autoApprove": true
   （文件与文件夹不存在则创建）
              ↓
③ GitHub Copilot 立刻进入 YOLO 模式
              ↓
④ 攻击执行终端命令（条件注入可按操作系统决定执行什么）
              ↓
⑤ 实现「由提示词注入驱动的远程代码执行」
```

> 作者演示了：左边是带提示词注入的演示文件，右边是开发者在聊天框中与之交互，
> **随后计算器弹了出来**。

## 攻击面不止 YOLO 模式

微软询问是否还有其他信息时，作者进一步发现**更多可写入口**：

- **`.vscode/tasks.json`** —— AI 同样可写
- **添加伪造的恶意 MCP 服务器**
- **重新配置项目的用户界面与设置**

作者还注意到一个新趋势：**开发者常常同时使用多个智能体**，因此还存在
**覆盖其他智能体配置文件**的威胁（如允许执行 bash 命令的白名单、添加 MCP 服务器等）——
因为这些文件**通常也放在项目文件夹里**。

## 更严重的延伸：AI 病毒

> **这意味着可以构建真正的「AI 病毒」**——附着在文件上，随着开发者下载并与被感染
> 文件交互而**自我传播**。

传播路径：

```
攻击者嵌入指令
   ↓
获得代码执行后，投放额外恶意软件
   ↓
恶意软件感染其他 Git 仓库（以及 RAG 知识源）
   ↓
嵌入恶意指令，提交改动，甚至强制推送到上游
   ↓
其他开发者毫不知情地继续传播被感染的代码
```

> **后果**：开发者机器可被接入僵尸网络（作者称之为 **ZombAIs**）；
> 可被劫持下载恶意软件、接入远程 C2 服务器——**为恶意软件、勒索软件、信息窃取器
> 打开了大门**。

## 不可见指令（更隐蔽的变体）

如果指令以**注释**形式明文嵌入，很容易被开发者发现。作者构造了**用户不可见的载荷**：

> 这种方式**不够可靠**，但确实有效。

作者的诚实提醒（**这点很重要**）：

- 不可见指令常导致利用**非常不稳定**
- 也会**经常被模型直接拒绝**
- VS Code 通常会对 Unicode 字符显示**视觉提示**
- 并非所有模型都易受此类攻击

> 「但攻击（和模型）会随时间变强。」

## 作者的修复建议

> **理想情况下，AI 在未经人类事先批准的情况下不应能修改文件。**
> 许多其他编辑器会**显示 diff**，交由开发者批准。

> **Keep looking out for such design flaws, these should be easily caught during threat modeling.**
> （继续寻找这类设计缺陷——它们本应在威胁建模阶段被轻易发现。）

## 可迁移到实践的四条

1. **把「AI 可写配置文件」列为安全评审项**——尤其是项目目录内的
   `.vscode/`、智能体配置、MCP 服务器清单。
2. **不要把智能体设成自动批准模式**（`autoApprove` 之类），尤其在含不可信代码的仓库中。
3. **clone 仓库前审查其中的 IDE/智能体配置**——它等价于可执行载荷。
4. **威胁建模时假设智能体会自我提权**，把它当作对抗性参与者而非可信组件。
