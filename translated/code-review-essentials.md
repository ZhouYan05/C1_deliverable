## 软件团队的代码审查要点

2015年2月9日

代码审查是任何协作型软件项目中不可或缺的组成部分。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员以及代码库本身始终朝着正确的方向前进。

代码审查是一个强大的工具，它能够：

- 帮助团队成员在系统不断变化时同步更新自己对系统的认知模型
- 确保改动正确地解决了问题
- 就设计的优缺点展开讨论
- 在缺陷流入生产环境之前将其捕获
- 保持代码风格与组织结构的一致性

把这些好处看作一个需求层次结构会很有帮助。

## 让团队成员保持一致

代码审查最关键的作用，是让团队中的每一位成员都朝着正确的方向前进。你无法安全地修改一个你不了解的系统，因此代码审查能让整个团队在认知上保持对齐。当 Bob 为账务子系统提交拉取请求（PR）时，Amy 在审查 Bob 的代码的过程中，也在同步更新自己对该系统的认知模型。Amy 有机会就她不太理解的部分提出问题，而 Bob 则能借此阐明自己的设计决策，同时向他人讲解自己的工作，这对他也有好处。一个月后，当 Amy 需要修改账务子系统时，她对系统的认知模型早已是最新的，随时可以投入行动。她可以少花时间阅读代码、在脑中拼凑系统的全貌，把更多时间用于思考更高层次的抽象与设计。每个人都赢了，因为每个人都保持着同步。

## 执行一次出色的拉取请求（PR）

在你动手写下任何一行改动系统的代码之前，先问问自己以下几个问题：

- “这是我该做的事情吗？”客户、团队内部成员和其他各方总会提出相互竞争的需求。在深入投入之前先问这个问题，是让你在脑中理清优先级的好办法。迭代/冲刺计划会议等其他流程也有助于让这一点始终不偏离轨道。
- “团队是否已经一致认为这个改动是正确的？”如果没有，最好先通过邮件或当面发起一场设计讨论。在动手改动之前就让人们对设计达成一致，你的改动才更有可能被接受。
- “我该如何把这个改动拆分成易于审查和理解的、可消化的小块？”小的改动更容易思考和理解。只有当团队能快速领会你的改动时，高质量的讨论才会随之而来。如果你的改动过于庞大，同事们会看得目光呆滞，你可能只会收到几条关于代码风格的小挑剔。
- “我打算如何测试这个改动，以消灭缺陷并确保其正确性？”你也许有 QA 部门，但作为开发者，交付高质量、可正常运行的软件仍然是你的职责。易于测试的软件通常耦合度更低、被拆分成更小的模块，也更容易推理。你需要为你的所有改动制定测试计划。

我发现，提前回答这些问题，从长远来看为我省去了很多头疼的麻烦。你最不希望发生的事情，就是花好几天时间写出一套改动，结果却因为根本性的设计缺陷或团队意见分歧而被否决；或者因为没人能验证其正确性而让你的改动被搁置。再次强调，目标是在改动系统的同时，让其他团队成员始终了解你的改动。问问自己打算如何把工作拆成易于处理的小块并逐一测试这些小块，这在很多方面都大有裨益：

- 它能降低风险
- 它让改动更容易推理
- 它推动你走向更好的设计

你宁可用手术刀划出许多小而精准的切口，也不愿用砍刀劈出一道巨大的伤口。在大多数增量开发的场景中，我倾向于手术刀式的开发方式，而把砍刀留到需要删除大块死代码的时候再用。

## 发送拉取请求（PR）

好，现在你已经获得了团队的认可，确认你的改动是好的，并且实现了你当初设想的设计。那么，实际发送拉取请求（PR）最有效的方式是什么？你一直在努力完成你的改动，你希望团队的其他成员关注你的拉取请求（PR）并尽快给出反馈。你该怎么做呢？

还记得我前面说过，代码审查最重要的部分是让团队的集体认知模型保持良好对齐吗？你的其他同事很可能正在做与你完全不同的事情，也许是在系统中完全不同的部分。他们的大脑处于完全不同的上下文之中，所以你必须通过给他们提供审查所需的、有用的引导来克服这一点。这意味着你要条理清晰地描述你做了哪些改动、为什么做这些改动，以及任何他们光靠阅读代码无法获得的相关信息。别让你的同事做超出必要的脑力劳动。

让我们来看看一些拉取请求（PR）描述的好与坏的示例：

糟糕的示例：

```
标题：修复未初始化内存的缺陷
描述：

这是之前 Bob 和我讨论过的那个缺陷。我在编译器上遇到了麻烦，但总算把它搞定了。想听听大家的意见。
```

如果你是这条拉取请求（PR）的开发者，请停下来，设身处地站在代码审查者的角度想一想。这个标题含糊不清，带来的问题比答案还多：内存缺陷在哪里？这个改动有多关键？Bob 和你之前讨论的缺陷究竟是什么？你在编译器上遇到了什么麻烦？这段描述没有提供任何关于该问题的有用上下文，也没有对你的改动做出任何有用的说明。如果这条拉取请求（PR）很长，审查者就不得不一头扎进代码里，绞尽脑汁地试图获取上下文，然后才有机会思考这个改动如何融入系统连贯的设计之中。

下面是一个改进后的示例，它有助于阐明这次改动集：

```
标题：修复因未初始化内存导致的启动时进程崩溃 [#54633]
描述：

这个缺陷会导致进程在启动时崩溃，原因是我们的统计 Counter 类中存在内存初始化错误。我和 Bob 讨论过这个问题，我们都认为这种崩溃是一种罕见的边界情况，不值得为此发布热修复（hot-fix）版本。以下是改动摘要：

 - 将底层的 int 变量移入类初始化器中，以防止 Counter 中出现未初始化的内存。
 - 重构了 Counter 的接口，以简化调用方的条件逻辑，并防止出现进一步的差一（off-by-one）计数问题。
 - 新增了一个能够复现该崩溃的单元测试。

测试：我已确认测试套件仍然通过，并手动验证了本地不再发生该崩溃。
```

这条拉取请求（PR）描述有几处改进：标题的描述性足够强，能给审查者提供简短的上下文，并吸引他们点开邮件了解更多。审查者知道这是一次进程崩溃（通常是非常糟糕的事情），而且还有一个缺陷报告编号，如果审查者有兴趣深入了解该问题，可以据此查阅更多详情。新的描述还概述了问题发生的位置，并帮助说明了这个修复有多关键。其中有一个摘要，列出了拉取请求（PR）中高层的结构性改动，让审查者甚至在查看代码之前就能对改动形成整体印象。代码审查者不应该对所发现的内容感到意外。这个示例还概述了所执行的测试，这将让审查者相信这些改动经过了深思熟虑和充分测试，可以准备合并了。让你的审查者轻松获得成功——让他们可以毫不费力地点击“合并”。

## 审查者：如何给出建设性反馈

审查流程中接下来要考虑的部分，是如何向你的同事给出建设性反馈。如果目标是清晰明确和保持一致，那么给出高质量的建设性反馈有助于每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- “这个设计行不通。”它为什么行不通？怎样才能改进？这样的表述会打击信心，也容易伤及自尊。
- “我不喜欢这个改动。”你为什么不喜欢？你希望改成什么样？不喜欢某个东西是可以的，但你应该清晰地表达你的想法，并就如何改进代码提供有用的线索。
- “你能把它重写得更清晰一些吗？”我现在的代码有什么问题？我该如何重写？哪里不清楚？这样的评论本身就不清晰，也没有给出一条简单的改进路径。

相反，应该这样说：

- “这段代码如何处理负整数？”这样的反馈很具体，能促使开发者自己把各种结果想清楚。作为审查者，你可能知道这段代码遇到负整数时会崩溃，但更好的做法是让开发者自己领悟到这一点。这样的问题也可能反映出测试存在缺口，或者需要进一步明确范围。
- “这部分让我感到困惑，我不明白为什么 A 类会和 B 类打交道。”如果开发者没有提供有用的描述，代码结构也不够整洁，这类评论有助于推动设计更清晰、代码更干净。
- “看起来你在这里打破了接口边界。这会对用户产生什么影响？”你指出了你注意到的问题，并善意地假定他们是有意为之。现在他们可以仔细思考打破接口边界所带来的、尚未被察觉的各种后果，然后要么为自己的决定给出理由，要么选择修改。

总的来说，把反馈包装成问题，是推动清晰性和正确性的好方法，同时也能帮助开发者在未来改进自己的设计。高质量创意写作小组通常就是这样互相给反馈的。在创意写作的场景中，说“我不喜欢这个角色”之类的话是有害的，而同样的评论可以更清晰地改写为：“在第一章里，你的角色温暖而富有同情心，现在他却变得冷冰冰的。在我看来，他不像一个真实的人。”现在就有了具体的反馈，可以进一步澄清，从而把问题弄清楚。

程序员喜欢解决问题、指出毛病，所以从本性上讲，他们喜欢发现并指出缺陷。把代码审查当作一种通过挑出同事代码中的问题来证明自己有多聪明的途径，这确实很有诱惑力。别这么做。代码审查是让更多双眼睛审视改动、找出关键问题的一种方式，但你的目标应该是：以鼓励团队成员提升技能的方式进行审查，同时解决眼前的问题。

## 风格要点

花括号的位置、变量/函数命名、缩进和空格问题都应该处理，但它们并不是高质量代码审查的核心目的（请注意，我把它们放在代码审查金字塔的顶端）。如果你发现你的团队把 90% 的时间都花在挑剔缩进和变量名上，那么你可能是在把大家的时间浪费在那些大部分可以自动化处理的事情上。写一份风格指南，在代码提交（check-in）时强制统一缩进和空格问题，把时间花在关注更高价值的问题上。我并不想贬低风格一致性的重要性。恰恰相反，拥有一致的惯用风格，是让代码库易于阅读和理解的最简单方法之一。不过，如果你把所有的代码审查都花在这些简单琐碎的任务上，请扪心自问：你是否在回避那些更难、更重要的工作——让团队保持认知对齐、思考更高层次的设计？
