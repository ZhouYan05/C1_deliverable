# 精读笔记：软件团队的代码审查要点

> 原文：Code Review Essentials for Software Teams（Blake Smith，2015-02-09）
> ⚠️ 本笔记为**提炼与讲解**，非逐段译文。原文版权归作者所有。
> 📌 注意：本文写于 2015 年，**早于 LLM 编码工具普及**，但其流程原则在 AI 时代
>    依然成立——甚至因为 AI 产出量大，**更**需要这套约束。

## 一句话结论

**代码审查的首要目的不是抓 bug，而是让整个团队的心智模型保持同步。**
作者把代码审查的收益看作一个**需求层次金字塔**。

## 代码审查的五个作用

1. **帮助团队成员在系统变化时更新其心智模型**
2. **确保改动确实解决了问题**
3. **为设计的优缺点打开讨论**
4. **在缺陷进入生产前抓住它们**
5. **保持代码风格与组织结构的一致性**

> 作者强调这些收益**有先后层次**——第 1 条（保持团队同步）是最关键的。

## 一、让团队成员保持同步

> **「你无法安全地改动一个你不理解的系统。」**

作者用一个具体场景说明：

- Bob 为**会计子系统**提交 PR
- Amy 在审查过程中**持续更新自己对该系统的认知模型**
- Amy 有机会**提问**她不理解的部分
- Bob 则获得**澄清自己设计决策**的机会，同时也在**向别人讲解**自己的工作

一个月后，当 Amy 需要改动会计子系统时：

- 她的心智模型**已经是最新的、可以直接动手的状态**
- 她**花更少时间读代码、在脑中拼凑系统**，而**花更多时间思考更高层的抽象与设计**

> **「每个人都赢，因为每个人保持在同一起跑线上。」**

## 二、开写之前先问四个问题

> **「在你写第一行改变系统的代码之前，先问自己以下问题：」**

### 1. 「这是当前该做的事吗？」

客户、内部成员与其他各方的需求**永远在竞争**。这是**在你一头扎进去之前**理清优先级的
好方法。迭代 / 冲刺计划会议之类的其他流程也有帮助。

### 2. 「团队是否已经认同这个改动是对的？」

如果没有，**最好先通过邮件或面谈展开设计讨论**。**在改动之前**就让大家对设计达成一致，
你的改动被接受的概率会高得多。

### 3. 「我如何把这次改动拆成易于审查和理解的、可消化的小块？」

- **小改动更容易思考和理解**
- 良好的讨论源于团队能**快速理解**你的改动
- 如果改动**太庞大**，同事会「眼神放空」，你只会收到几条格式挑刺

### 4. 「我打算如何测试这次改动，以杀死 bug 并确保正确性？」

你可能有 QA 部门，但**交付可用的软件仍然是开发者的责任**。容易测试的软件通常：

- **耦合更低**
- 被**拆成更小的块**
- **更容易推理**

> **你为所有改动都需要有一份测试计划。**

作者的经验：提前回答这四个问题**长期来看省掉了大量麻烦**。你**最不希望发生的事**是：
花几天写完一个改动，最后却因**根本性的设计缺陷或团队分歧**被拒；或者因为没人能验证
其正确性而被卡住。

拆分改动在多个方面都有帮助：**降低风险**、**让改动更易推理**、**推动你走向更好的设计**。

> **「你宁愿用手术刀做许多次小而精准的切割，也不要用砍刀留下一道巨大的伤口。」**
> 作者偏好**手术刀驱动的开发**（多数增量场景），
> 只在**该删除大块死代码**时才动用砍刀。

## 三、如何提交 PR

前提已达成：团队认可你的改动，你也实现了目标设计。**怎样提交才最有效？**

### 关键前提

> 你的同事**很可能在完全不同的地方工作**，大脑处于**完全不同的上下文**中。
> 因此你必须**提供他们完成审查所需的有益指引**——这意味着：

**写一份组织良好的描述**，说明：

- 你**做了什么改动**
- **为什么**要这么做
- 任何**只看代码得不到**的其他相关信息

> **「不要让你的同事做超出必要范围的脑力劳动。」**

### 反例（反面教材）

```text
Title: Fix uninitialized memory bug
Description:
This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work.
Let me know what you guys think.
```

**问题**：标题含糊，**提出的问题比答案多**——

- 内存 bug 在哪里？
- 这个改动有多关键？
- 之前和 Bob 讨论的到底是什么 bug？
- 编译器出了什么问题？

如果 PR 很长，审查者**必须先一头扎进代码做脑力体操以获得上下文**，
之后才有机会思考这个改动如何融入系统的整体设计。

### 正例（改进后）

```text
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

 - Moved the underlying int variable into the class initializer
   to prevent ununitialized memory in the Counter.
 - Reworked the Counter interface to simplify caller conditional
   logic and prevent further off-by-one counting problems.
 - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```

**改进之处**：

| 改进点 | 效果 |
|---|---|
| 标题有描述性 | 给审查者简短上下文，吸引他们点开看 |
| 说明是「进程崩溃」 | 这通常是**很严重**的事 |
| 附 issue 编号 | 想深入了解的审查者可自行查阅 |
| 交代问题出在哪里 | 帮审查者判断修复的**关键程度** |
| 改动摘要 | 在看代码之前就建立改动的**整体心理图像** |
| 说明做了哪些测试 | 给审查者信心：改动**经过深思、经过测试、可以合并** |

> **「代码审查者不该对他们发现的东西感到意外。」**
> **「通过让审查者轻松点下 merge，为他们的成功铺路。」**

## 四、审查者：给出建设性反馈

> 审查者**要避免这样说**（有害、伤害信心与自尊）：

- ❌ **「这个设计是坏的。」**——为什么坏？怎么才能更好？
- ❌ **「我不喜欢这个改动。」**——为什么不喜欢？你希望是什么样？
  不喜欢没关系，但你**应该把想法讲清楚**并给出有益线索。
- ❌ **「能不能重写得更清楚一点？」**——我现在的哪里有问题？该怎么重写？
  **这类评论本身就是不清楚的**，也没给出简单的前进路径。

> **应该这样说：**

- ✅ **「这段代码如何处理负整数？」**
  反馈**具体**，让开发者**自己**推演结果。
  也许审查者知道负整数会崩溃，但**让开发者自己直觉到这一点更好**。
  这类问题还可能**暴露测试缺口**或范围定义不足。
- ✅ **「这一节我看着困惑，不理解为什么类 A 要和类 B 通信。」**
  如果开发者没提供有益描述、代码结构也不清晰，**这类评论能推动设计清晰化与代码整洁**。
- ✅ **「看起来你在这里打破了一个接口边界。这会如何影响用户？」**
  你指出了注意到的问题，并**善意地假定对方是有意为之**，
  对方就能推演打破接口边界的**潜在连锁影响**，并给出理由或选择修改。

> **总体而言，把反馈包装成「问题」是通往清晰与正确性的好方法，**
> **同时帮助开发者未来改进设计。**

### 类比：高质量创意写作小组

高质量的创意写作小组**就是这么互相给反馈的**。说「我不喜欢这个角色」是有害的；
同样的意见可以重构得更清晰：

> 「第一章里你的角色温暖而富有同情心，现在他却冷漠如冰。他在我看來不像一个真实的人。」

现在就有了**具体的反馈可以被澄清**，从而把问题理清楚。

### 最重要的警告

> **程序员天生喜欢解决问题、指出问题**——他们本质上喜欢发现并指出缺陷。
> 这很容易让人把代码审查当成**证明自己有多聪明**的方式。
> **不要这样做。**

代码审查的目的是**让一双额外的眼睛检查改动、找出关键问题**，
但你的目标应当是：**以鼓励团队成员提升技能的方式进行审查，同时修复当前的问题。**

## 五、风格问题

> 大括号位置、变量 / 函数命名、缩进与空格问题**应该处理**，
> 但它们**不是好代码审查的核心目的**。

作者的判断标准很直接：

- 如果团队**把 90% 的时间花在挑缩进和变量名上**，
  那你很可能**在浪费所有人的时间**去处理一件**本可以大部分自动化**的事
- 正确做法：**写一份风格指南，在代码签入时自动强制执行缩进与空格问题**，
  把人的时间**专注在更高价值的问题上**

但作者也**不贬低一致风格的重要性**——相反：

> **「保持一致、符合惯用法的风格，是让代码库易于阅读与理解的最简单方式之一。」**

关键区分：

| 该自动化 | 该人工 |
|---|---|
| 缩进、空格、命名规范 | 设计是否正确 |
| 用 linter / pre-commit hook | 改动是否解决了真问题 |
| | 心智模型是否同步 |

> 「如果你的全部代码审查都聚焦在这些简单任务上，问问自己：
> **你是不是在回避那些更困难、更重要的工作**——保持团队心智同步、
> 思考更高层的设计。」

## 可迁移到实践的四条

1. **提交前回答那四个问题**（该不该做 / 团队是否认同 / 如何拆分 / 如何测试）——
   这是成本最低的返工预防。
2. **PR 描述写给「不在你上下文里的人」看**——他们的大脑在别处。
3. **把反馈写成问题，不是判决。**
4. **风格问题交给 linter，人脑留给设计。**
