# GitHub Copilot：通过提示词注入实现远程代码执行（CVE-2025-53773）——Embrace The Red

本文讨论的是一项重要但也令人不安的提示词注入（Prompt Injection）发现——它可导致开发者机器上的 GitHub Copilot 和 VS Code 被完全攻陷。

实现方式是通过修改项目的 settings.json 文件，将 Copilot 置于 YOLO 模式。

正如几天前在 Amp 中所描述的，智能体（Agent）中一个可能被忽视的漏洞模式是：如果智能体可以写入文件、修改自身配置或更新与安全相关的设置，就可能引发远程代码执行（RCE）。这种情况并不罕见，是进行安全审查时始终需要关注的领域。

## 背景研究

在研究 VS Code 和 GitHub Copilot 的智能体模式（Agent Mode）时，我注意到了一个奇怪的行为——它可以在未经用户批准的情况下，创建工作区中的文件并向其中写入内容。

这些编辑会立即持久化，而不是以内存中可审阅的差异（diff）形式存在。修改会立刻写入磁盘。

作为红队人员，你知道这很可能不是什么好事——所以我开始研究能否利用这一点来提升权限并执行代码。

### YOLO 模式

接下来，我研究了 VS Code 中依赖项目/工作区文件夹内设置的各项功能，很快发现了一个有趣的功能。

事实证明，在 .vscode/settings.json 文件中可以添加以下行：

`"chat.tools.autoApprove": true`

这将使 GitHub Copilot 进入 YOLO 模式。

它会禁用所有用户确认，我们可以运行 Shell 命令、浏览网页等等！

有趣的是，这是一个实验性功能，但默认情况下仍然存在。我既没有下载特殊版本，也没有将 VS Code 整体设置为实验模式。

此外，它在 Windows、macOS 和 Linux 上均可生效。

## 漏洞利用链解析

劫持 Copilot 并提升权限的概念验证（PoC）漏洞利用链如下：

- 攻击始于植入在源代码文件、网页、GitHub Issue、工具调用响应或其他内容中的提示词注入。载荷还可以使用不可见文本作为指令。
- 提示词注入首先在 ~/.vscode/settings.json 文件中添加 "chat.tools.autoApprove": true 这一行。如果文件夹和文件尚不存在，则会自动创建。
- GitHub Copilot 立即进入 YOLO 模式！
- 攻击者运行终端（Terminal）命令。借助条件式提示词注入，我们实际上可以根据操作系统来决定运行什么。
- 我们实现了由提示词注入驱动的远程代码执行（RCE）。

下面这张截图展示了包含提示词注入的演示文件、右侧聊天框中开发者与该文件的交互，以及弹出的计算器！

当然，任何其他提示词注入的投递途径——例如网页内容或来自模型上下文协议（MCP）服务器返回的数据——都是攻击角度。我只是将它放在源代码文件中，因为这样最容易测试。

## 将工作站加入僵尸网络——ZombAI

当然，这意味着我们可以将开发者的机器作为 ZombAI 加入僵尸网络。

此外，为了好玩，我们还可以修改 settings.json 文件，将 VS Code 切换为红色配色方案之类的。

但这还没完！这也意味着我们可以构建真正的 AI 病毒——它会附着在文件上，并在开发者下载和交互受感染文件时进行传播。

最后但同样重要的是，为了证明我们已完全控制开发者的主机，我们展示了 Copilot 可以被劫持来下载恶意软件，并加入远程命令与控制（C2）服务器。

这意味着恶意软件、勒索软件、信息窃取程序等的大门已经敞开。

令人不寒而栗。

## 构建 AI 病毒

看到这一点后，人们会意识到这基本上等同于允许创建病毒。攻击者可以嵌入指令，一旦获得代码执行能力，额外的恶意软件就可以攻陷其他 Git 项目（以及检索增强生成（RAG）源），嵌入恶意指令，并提交更改，甚至强制推送到上游。

随着其他开发者在不知情的情况下传播受感染的代码，这将导致进一步的扩散。

最后，我们还需要谈谈不可见指令！

注意：虽然这里使用不可见指令的演示在我这里多次成功，但使用不可见指令通常会导致漏洞利用非常不可靠，也常常被模型拒绝，而且 VS Code 通常会显示关于 Unicode 字符的视觉提示。然而，攻击（和模型）会随着时间的推移不断改进。同样值得强调的是，并非所有模型都容易受到此类不可见提示词注入攻击。

## 建议与修复

实际上，除了我分享的 YOLO 模式示例之外，还有更多攻击角度。当微软问我是否还有其他信息时，我进一步研究后发现还有其他存在问题的位置，例如 AI 可以写入的 .vscode/tasks.json，或添加伪造的恶意 MCP 服务器等，这些都可能导致代码执行。而且 AI 还可以重新配置项目的用户界面和配置设置。

最近我注意到，开发者经常使用多个智能体，因此还存在覆盖其他智能体配置文件的威胁（白名单 bash 命令、添加 MCP 服务器……），因为这些文件通常也位于项目文件夹中。

理想情况下，AI 在没有人类事先批准的情况下不应能够修改文件。许多其他编辑器会显示差异（diff），然后由开发者批准。

## 负责任的漏洞披露

在 2025 年 6 月 29 日报告该漏洞后，微软确认了复现步骤，并询问了几个后续问题。几周后，微软安全响应中心（MSRC）指出，这是他们已经在跟踪的问题，并将在 8 月修复。随着 8 月补丁星期二（Patch Tuesday）版本的发布，此问题现已修复。

向 Persistent Security 的 Markus Vervier 致谢，他也发现并向微软报告了此漏洞。你可以在这里找到他们的分析文章。同时也要向 Ari Marzuk 致谢，他似乎也同时发现了该漏洞。

感谢 MSRC 和产品团队的成员帮助缓解了该问题。

## 结论

这是 AI 智能体可能不守本分的又一例证！通过修改自身环境，GitHub Copilot 可以提升权限并执行代码，从而攻陷开发者的机器。正如我所发现的，这在智能体系统中并非罕见的设计缺陷。

请继续留意此类设计缺陷，这些缺陷本应能在威胁建模时轻易发现。
